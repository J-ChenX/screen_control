# 性能与长期稳定性优化

2026-09-20 已完成本轮优化、相关回归、三机隔离实测与既有环境发布。保持 Go、React/TypeScript 和现有 Python 运维工具，不更换语言、网络边界或设备角色。本结果不替代长期浸泡测试、并发容量测试或 G0/G3 正式验收。

## 结论与范围

主要瓶颈是文件下载逐块等待确认、设备指标同步阻塞请求、目录单帧过大及大目录全量 DOM。语言运行速度不是这些问题的主要原因。优先修复协议、等待链路和资源上限，比整体迁移 Rust/Go 更直接。

| 项目 | 已完成的处理 | 稳定性约束 |
| --- | --- | --- |
| 文件传输 | 协商最多 8×256 KiB 窗口、累计确认、串行读取和写入 | 未协商仍用旧协议；反压限制在途正文；完整确认后提交；取消与断线不重放 |
| 迟到数据 | 新窗口帧携带八字节下载标识，正文偏移 12；旧模式仍为 4 | 同时校验下载标识和连接代次，丢弃已取消下载的数据 |
| 目录浏览 | 后端每页 256 项，前端超过 300 项启用虚拟网格 | 会话内游标绑定路径、请求和页号；及时关闭句柄；旧端超大目录返回可恢复错误 |
| 状态与会话 | 新鲜设备状态与展示指标分离；最多每 5 秒共享采样 | 独立 3 秒截止、子进程管道额外等待最多 250 ms；指标最多缓存 15 秒；不缓存权限或在线判断 |
| 界面更新 | 排序缓存、选择集合、传输进度约 100 ms 限频 | 保留键盘、手机、覆盖确认及失败提示 |
| 文件夹复制 | gzip 使用 BestSpeed | 保留完整临时归档、声明长度及安全解包；未引入未经验证的未知长度流式协议 |
| 桥接入口 | 文件 WebSocket 入口执行 1 MiB 帧限制 | 超限关闭码 1009，与文件进程的帧限制一致 |

## 实机结果

全部文件测试使用本次创建的普通用户临时目录，不覆盖已有用户文件。以下为短时测量，不承诺任意网络、磁盘或负载下保持相同比例。

| 测量 | 发布前 | 发布后 |
| --- | --- | --- |
| 可信入口状态查询，20 次请求中位值 | 405.74 ms | 19.27 ms |
| 同一批状态查询最大值 | 445.82 ms | 25.11 ms |
| nix：8 MiB 下载，真实 SSH 文件进程 | 7.20 MiB/s | 18.04 MiB/s |
| Windows：8 MiB 下载，真实 SSH 文件进程 | 4.75 MiB/s | 30.28 MiB/s |
| nix：8 MiB 上传 | 10.60 MiB/s | 30.03 MiB/s |
| Windows：8 MiB 上传 | 12.75 MiB/s | 27.16 MiB/s |

不同轮次的候选测试中，nix 下载约 24 MiB/s，Windows 约 12～31 MiB/s，说明短时结果存在波动。健康接口、身份 API、三个设备收藏 API 均通过；收藏数据及服务单元保持一致。

三台已安装文件进程均通过上传/下载 SHA-256、故意短写覆盖失败后的原文件 SHA-256、空文件、602 项目录三页遍历、无重复项和临时上传文件清理检查。回执均协商为窗口 8。

真实浏览器经已部署门户完成 8 MiB 上传、跨设备复制和下载，未模拟 API 或文件协议：nix 使用 1440 像素桌面视口，Windows 使用 390 像素手机视口，复制目标均为 echova 隔离目录；来源下载与目标文件 SHA-256 均一致，无页面异常。两次跨设备复制完成约为 905/849 ms，包含浏览器编排与完成提示，不等同于纯链路吞吐。两侧 600 余项目录均保持少于 200 个挂载选项。

## 资源和隔离实验

- 原始 16,380 字节逐块下载在额外等待 50 ms 时约 0.306 MiB/s。最终协议的 4 MiB 隔离实验，确认额外等待 10 ms 时旧/新分别为 1.518/96.070 MiB/s；50 ms 时为 0.309/24.670 MiB/s。哈希均一致。这是人为确认延迟，不是实网带宽。
- Linux `/usr/bin/time` 测得文件进程峰值 RSS：旧端处理 8 MiB 为 8,064 KiB，新端 8 MiB 为 8,288 KiB，新端 128 MiB 为 9,140 KiB。测试包含上传、下载、失败覆盖及再次完整下载；不包含浏览器、SSH 和整个服务的内存，不能替代并发容量测试。
- 8 MiB gzip CPU 基准中，伪随机二进制约 114→651 MB/s，重复 JSON 约 795→2494 MB/s。二进制压缩后接近原大小，JSON 压缩比例由 0.341% 增至 0.733%；每次压缩分配约 0.81→1.21 MB。接受此体积和内存代价来减少压缩等待。
- 原始 20,000 项目录超出 1 MiB 单帧并使进程退出；新目录专项验证后端有界分页及旧端可恢复错误。前端 20,000 项的桌面、手机测试覆盖虚拟渲染、跨未挂载项目的键盘导航、旧端响应、过期回复和超时。

## 桌面测量与决策

被动实机探针不注入键鼠、不记录画面正文、不锁屏，只结束自身创建的会话。Windows 发布后连接状态约 370 ms、首次绘制约 680 ms；发布前单次连接约 1,374 ms、首次绘制约 1,323 ms。样本少且画面不受控，不解释为严格的首帧性能对照。

Windows 发布后的两个 20 秒观测窗口：正常模式 3840×2160 接收约 26.0 MB，流畅模式 1920×1080 约 12.1 MB；同步绘制调用累计约 36/19 ms，未观测到长任务。nix 发布前正常模式为 2880×1800，几乎静止，20 秒仅约 15.7 KB；切换流畅后分辨率未观察到变化，不能外推 Windows 的降分辨率效果。nix 发布后连接状态约 275 ms、首次绘制约 490 ms，两个观察窗口仍几乎静止。

保留现有流畅模式和 JPEG 图块链路，本轮不修改默认编码或强制开启 WebRTC。这些数据不能给出编码延迟、完整解码耗时、交互端到端延迟或受控动态 FPS，也未证明浏览器绘制是主要瓶颈。后续编码或直传工作应先建立受控动态画面和分段时延基准，并遵守原工作包前置门。

已通过：

- Go 全包测试、`internal/g0bridge` 与 `internal/g0files` 最终竞态检查，包含真实 WebSocket 超限帧测试；Windows 文件进程交叉构建。
- 前端 55 项测试、类型检查和生产构建。
- 原有文件浏览器完整回归；新旧端混用、失败不提交、空文件、过期下载标识、17 MiB OPFS 下载 SHA-256 专项；大目录桌面与手机专项，截图已检查。
- 三台候选及已安装文件进程隔离检查；真实门户桌面连接与真实浏览器文件端到端检查。

复测入口：`tests/performance/file-transfer.mjs`、`file-worker-live.mjs`、`files-browser-live.mjs`、`desktop-live.mjs`。使用项目锁定工具链。实机脚本从环境取得可信入口、既有 SSH 映射和预先创建的 `screen-control-perf-*` 临时目录，不应指向用户工作目录。`file-worker-live.mjs` 支持 `SCREEN_CONTROL_PERF_BYTES` 指定 8～128 MiB 测试大小，默认 8 MiB；浏览器实机脚本使用 `SCREEN_CONTROL_PERF_FIXTURES` 的三个设备目录映射。脚本不负责创建、授权或自动删除任意指定目录。

发布前用初始工作区快照重建，并逐一比对已部署桥接、门户和三台文件进程的哈希。桥接从已核验的部署源目录隔离构建，只引入本次相关桥接改动；门户和文件进程基线也与线上一致，未顺带发布其他未完成工作。既有版本目录保留，可独立回滚。

发布期间两次校验脚本问题触发恢复：一次为 Windows 安装输出编码，一次为把每次变化的 API 请求编号纳入收藏哈希。已确认并修正检查逻辑，三台旧文件进程哈希及收藏文件均恢复/保持一致，随后重新发布成功；其中第二次实际执行了门户旧版本恢复及健康检查。

当前套件版本目录保存 `performance-release.json`、`rollback.sh`、`optimization-backup/`（旧版本指针、服务单元及收藏备份）。本机文件进程恢复入口为 `optimization-backup/rollback-worker.sh`；nix 和 Windows 在本次已登记的文件进程 staging 目录保存旧指针及 `rollback.sh` / `rollback.ps1`，令牌记录于发布清单。没有修改服务单元、SSH 身份、监听范围、防火墙或网络配置。回滚不覆盖实时收藏数据。本次三台设备的隔离测试目录已清理，临时预览已停止；最终服务为 active/running，自动重启计数为 0，三台设备均在线。

## 后续稳定性边界

已完成本轮实现、验证和部署；尚未执行长期浸泡、多人并发容量、断电恢复或 G0/G3 正式验收。后续应优先观察状态查询尾延迟、传输错误率、进程 RSS/句柄数及断线清理，再决定是否扩大窗口或调整编解码。前端目录元数据仍随项目数增长，虚拟网格仅限制 DOM；更大规模目录需要单独设计服务端排序/筛选与分页契约。不要仅凭当前短测试进行全仓语言迁移。
