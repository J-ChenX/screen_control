# Ubuntu Rust 代理更新记录（2026-09-29）

## 范围与来源

本轮先将已登记 Ubuntu 22.04.5 x64 设备 `nix`、`echova` 同步到 Rust 原生代理，随后补齐同系统的 `lerrem`。前两台结果保留如下，`lerrem` 的独立记录见末节。沿用 Windows 本轮使用的默认构建组合和最后分片按需扩容策略，排除五个可选 C 生命周期补丁；另补齐 Linux X11 主循环的暂停处理。Windows 工件、Go 门户、普通用户文件进程及前端运行产物没有更换。

最终 Linux 工件 SHA-256 为 `e9747a1857b8b9b143af651cdf9b9b4ce94cc05f040f107da509621e721f5b27`，Rust 静态库为 `f0c163e170cdb7c20ff5a3dba41ec64bedaea9769e5067196cbddd24ae792980`。源码、补丁、测试和各设备状态由[Linux 工件清单](../../deploy/g0/meshagent/rust-native/linux-runtime-manifest.json)关联。

Rust 接管共享 WebSocket 帧、分片所有权，以及 Linux XImage 转换、图块复制、变化校验与光标叠加边界；X11 资源、JPEG 编码及部分连接生命周期仍由 C 管理。最后分片局部分配减少不等于整机内存下降。

## Linux 暂停修正

既有 Linux 主循环处理 `MNG_KVM_PAUSE` 时只更新标志，没有据此停止采集。最初仅观察固定时段画面计数的探针可能因桌面静止而误判；加强检查在暂停排空后主动请求刷新，两台旧版均未通过。

现在主循环在读取控制管道后检查暂停标志，关闭本轮显示连接并等待 50 毫秒，再继续处理控制消息。暂停期间不生成新图块，恢复、刷新和退出仍可处理；不改变输入权限或协议字段。最终候选的两台实机会话均通过暂停中刷新不出图、恢复后新画面、Ctrl 按下/释放消息及普通结束检查。输入协议没有应用确认，因此只能证明发送了两条消息及后续画面可用。

## 更新与回滚

使用 `linux-canary.py` 更新既有服务，替换前建立十分钟 root 自动回滚，备份旧二进制、固定校验清单及身份快照。保留与回滚共用互斥锁，只有运行工件、主进程、备份和规则一致时才能显式保留。保留后仍可执行备份目录中的恢复脚本。

`nix` 已演练从候选恢复旧二进制及原校验清单，并在保留当前身份数据库的情况下重新建立真实会话；带暂停修正的前一构建也已恢复并通过服务健康检查。最终构建使用相同源码，重新构建后按最终摘要验证。现有身份数据库没有格式迁移，恢复脚本不自动回退数据库。

两机继续使用既有 cgroup 网络规则、固定摘要检查、768 MiB 内存硬上限、128 MiB Swap 上限和整组 OOM 清理。没有新增服务监听、修改防火墙策略或重启主机；重启的仅为既有 MeshAgent 服务。

两台均已保留最终版本；每台保留前六轮、保留后另启浏览器六轮桌面/手机会话通过，合计 24 轮，结束后浏览器位图归零、画布缩至 1×1。保留前两机各采样 90 次，间隔两秒另加采集耗时，主 PID 未改变、重启计数为零：

| `nix` | 34.54 / 50.55 / 15.57 | 仅主进程，采集子进程已退出 |

这些是非受控桌面内容下的短时采样，没有同负载旧版内存对照，不能计算性能提升比例。`echova` 的进程组回收仍是明确未验证项，不因会话检查通过而关闭。最终逐机保留状态、会话轮次和保留后采样结果见工件清单。原始探针与健康记录保存在本次被 Git 忽略的本地证据目录，公开清单只保留摘要及统计。此次交付属于可回滚运行观察，不宣称 G3、长期内存回收、完整画质/输入或约 11 天故障窗口已正式验收。
