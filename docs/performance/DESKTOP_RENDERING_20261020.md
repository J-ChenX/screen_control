# 桌面动态画面优化与验证（2026-10-20）

## 问题与本轮范围

用户报告 Windows 控制 lerrem 时，移动内容出现条纹、重影，静止后改善但不完全清晰。当前运行的 Linux 代理摘要与已登记 Rust 工件一致。隔离检查确认三个问题：浏览器串行解码、逐块绘制且没有等待时间背压；画质切换不刷新静止区域；Linux 代理只记录缩放参数，没有执行缩放。

本轮修改已有门户的参数与图块管理，不更换技术栈、代理工件、传输协议或设备角色。Linux 流畅模式改用实际支持的降帧率与压缩，不把半分辨率当作已实现能力。完整帧边界需要代理端扩展，本轮不宣称消除所有采集或显示撕裂，也不宣告 G0/G3 正式验收。

## 实施方案

1. 普通模式使用 JPEG 质量 85、原分辨率和 40ms 采集间隔；流畅模式使用质量 45 和 80ms 间隔，Windows 另外使用半宽高。切换时先发送压缩设置，再请求完整刷新，防止静止区域保留旧画质。
2. 最多四路解码小图块。JPEG SOF 尺寸预读用于计算像素预算，合计 8 Mi 像素；未知尺寸按完整画布估算。单张超过预算的合法大图仍可独占解码。解码完成而尚未绘制的位图继续占并行名额和像素预算，避免解码乱序造成内存堆积。
3. 保持协议序号，按浏览器刷新周期批量绘制，并在绘制后关闭位图。较晚图块先解码完成时等待较早图块，不得因正常乱序触发清理或反向覆盖画面。
4. 保留既有压缩字节和图块数量上限，增加单调等待时间检查：150ms 暂停采集；多图块积压达到 750ms 时清理旧代次，并请求完整刷新。恢复顺序为先刷新、后继续采集；恢复刷新至少间隔两秒。迟到解码结果关闭，不写入新画面；单张大图允许完成，不因普通等待阈值反复拒绝。
5. 保留会话、输入和文件权限边界。异常刷新不重放输入，不锁屏，不延长会话；结束时清理定时器、绘制回调、位图、协议缓冲和画布后备存储。

## 验证方法与结果

### 隔离逻辑与浏览器

- 锁定工具链的前端 81 项测试和类型检查通过；新增覆盖四路乱序解码、按刷新周期批量绘制、大图独占预算、等待时间背压、过期恢复、先刷新后恢复、退出清理及画质刷新。
- 锁定 Playwright Chromium 151.0.7922.34 的 `desktop-performance`、`desktop-mobile`、`desktop-files`、`desktop-lock-exit` 场景通过，覆盖桌面、手机横竖屏及 320px 窄视口。合成截图没有真实屏幕内容。
- 使用线上公开的实际 MeshCentral `common.js`、`agent-desktop.js` 和新旧图块管理器，分别运行三轮 60 个合成 JPEG 图块。每次解码人为附加 15ms 延迟，模拟受限控制端；最终 Canvas 与同一 JPEG 的按序参考绘制逐通道比较。

| 指标 | 原实现 | 本轮实现 |
|---|---:|---:|
| 排空中位时间 | 934ms | 261ms |
| 单轮时间 | 934 / 930 / 934ms | 261 / 261 / 265ms |
| 最终不同通道数 | 0 | 0 |
| 保留位图数 | 0 | 0 |
| 位图峰值 | 1 | 4 |
| 少量图块积压时暂停次数 | 0 | 1 |

该受控负载下排空时间缩短约 72%，不等于真实 Windows 的网络延迟或帧率提升 72%。协议没有完整帧边界，批量绘制只是减少跨刷新周期的新旧图块混显。

### 原生隔离检查

从固定归档、当前补丁及锁定 Rust 库编译实际 `getTileAt` 调用点，对 240 帧合成移动及停止画面检查增量矩形是否覆盖全部变化像素：273 个数据包，未发现漏覆盖。这不覆盖 X11 动态采集、网络及最终 JPEG 像素误差。

同一 640×480 合成图像经实际 C JPEG 编码与解码，对照质量参数：

| JPEG 质量 | 编码字节 | 平均通道绝对误差 |
|---|---:|---:|
| 45 | 44,948 | 3.33502 |
| 60 | 52,705 | 2.80690 |
| 85 | 81,737 | 1.84767 |

此图像上质量 85 相比 60 平均误差减少约 34%，编码量增加约 55%。提高质量有带宽代价，流畅模式仍用于受限链路。另一静止画面对照中，45 切到 85 后代理发送 0 个图块，强制刷新后发送新图块；本轮通过显式刷新修复该触发条件。

### 复现命令

公开脚本可从当前可信门户的 `/api/v1/vendor/common.js` 和 `/api/v1/vendor/agent-desktop.js` 获取到隔离目录，不需要桌面账号或会话令牌。旧实现使用本次修改前的 `memory.ts`，不改写历史证据。

```bash
mise exec -- corepack pnpm --dir web test
mise exec -- corepack pnpm --dir web typecheck
mise exec -- corepack pnpm --dir web build
mise exec -- node tests/browser/run.mjs desktop-performance desktop-mobile desktop-files desktop-lock-exit
mise exec -- node tests/performance/desktop-rendering.mjs <公开脚本目录> <旧版memory.ts>
```

`tests/performance/desktop-windows-live.mjs` 使用 Windows 已有 Node 与 Edge、独立临时配置和子进程 CDP 管道，通过实际门户控制登记 Linux 目标。它禁止发送远端键鼠，不保存画面、不锁屏，验证画质切换、解码异常恢复及普通结束。执行前显式配置当前可信 `SCREEN_CONTROL_CANONICAL_ORIGIN`，不得使用历史地址；测试使用系统 Edge，属于实机对照，不冒充锁定 Chromium 验收。

## 发布与限制

本轮先在隔离源码中复原线上首页及其引用资源，逐字节匹配。仓库 HEAD 与线上存在两个既有设备占位角色文案差异，已在隔离发布源码中排除；只叠加本次三个产品源文件，仓库中的角色定义没有修改。

门户静态处理器逐请求读取资源，故只发布新哈希资源并原子替换首页；旧资源保留，已有连接继续使用原脚本。备份原首页及可执行回滚脚本后检查健康、首页和引用资源。无需重启门户或其他服务；新脚本在完整刷新页面或通过新标签页打开门户后加载；仅在旧页面内返回再进入控屏仍可能使用旧脚本。

实际 Windows `jiang-chenx` → lerrem 的系统 Edge 155.0.4283.62 对照通过：实际画布为 2560×1440，普通 / 流畅 / 普通设置分别为 `[1,85,1024,40]`、`[1,45,1024,80]`、`[1,85,1024,40]`，两次画质切换及一次解码失败均通过同一会话恢复真实画面；普通结束成功。测试不发送远端键鼠，不保存屏幕图像。

另外在 lerrem 显示本轮创建的 320×192 合成窗口：不抢焦点、输入区域为空，完成 200 次移动后保持已知最终图案。Windows 经真实代理及中继收到 316 次绘制更新，位图峰值为 4；最终图案逐通道绝对误差超过 8 的数量为 0，平均通道误差约 0.00556。窗口、独立 Edge 配置及临时远端探针均已清理。该结果覆盖真实动态传输后的最终收敛，不代表用户所有应用及 GPU 渲染方式均已验收。

部署后本机回环健康及静态资源哈希通过；正常私网入口的健康、来源身份、设备快照、首页与资源均为 200。快照中 Windows、echova、lerrem 在线，nix 离线，未对离线设备做实机检查。私网首轮探测继承宿主代理配置返回 502，显式绕过代理后通过；没有修改宿主代理设置。门户 PID 及重启计数未变。回滚入口保存在当前主机私有 state 的 `screen-control/repairs/desktop-render-*`，恢复原首页即可切回旧资源。

尚未覆盖长期稳定性、真实持续拖动的端到端帧率和原始截图中所有条纹的唯一根因。Linux 半分辨率与代理帧边界协议仍未实现，后续若推进需单独覆盖输入坐标、协议兼容及原生部署回滚。
