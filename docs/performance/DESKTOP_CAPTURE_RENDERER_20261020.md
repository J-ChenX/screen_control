# 任务中心局部条纹的渲染器兼容修复（2026-10-20）

## 诊断范围

用户在近期整帧优化后仍偶发看到左上角红色竖条、内存提示框横向断裂，并确认本机屏幕正常、远程画面异常。本轮检查当前在线的 `lerrem`，没有把旧版增量图块的混显结论直接套用到此故障。

现场代理摘要与已保留的 2K 整帧工件一致。绕过代理、JPEG、网络和浏览器，使用 X11 `XGetImage` 读取根窗口时，仍得到同位置的红色条纹；通过 `XCompositeNameWindowPixmap` 读取任务中心自身窗口缓冲时也存在条纹和局部断线。这说明异常在编码之前已经存在，继续提高 JPEG 质量或刷新浏览器不能修复这批源像素。窗口缓冲读取本身不保证与合成器最终显示一致，因此不据此否定用户对本机屏幕的观察。

任务中心为用户安装的 Flatpak `io.missioncenter.MissionCenter` 1.2.0，使用 GNOME 50 / GTK 4.22.5 运行时。默认启动日志实际选择 `GskVulkanRenderer`，同时有 EGL 初始化失败及 llvmpipe 回退信息。临时使用 `GSK_RENDERER=cairo` 后标题恢复正常；再次恢复默认设置并重开应用，异常立即复现。这将问题缩小到该应用当前渲染路径与 X11 读回的兼容边界，尚未证明某个具体驱动或 GTK 内部缺陷是唯一原因。

## 已应用的修复与回滚

只对 `lerrem` 当前用户的任务中心设置 Cairo 渲染器：

```bash
flatpak override --user --env=GSK_RENDERER=cairo io.missioncenter.MissionCenter
```

当前应用已用相同设置重开并生效，后续正常启动继续使用该设置。此前的语言设置保留。没有更改全局 GTK 环境、驱动、依赖版本、显示模式或远控协议，也没有更新其他设备的应用配置。

GTK 官方提供该[渲染器选择方式](https://gnome.pages.gitlab.gnome.org/gtk/gtk4/running.html#gsk-renderer)。Cairo 是兼容回退，可能增加应用 CPU 开销，不应无条件推广到所有应用。此应用当前的动态图表和内存提示框已检查；未做长时间 CPU 对照或覆盖所有图形功能。

原应用级 override 文件、应用后的配置摘要、诊断计数和可执行回滚脚本保存在宿主私有 state 的 `screen-control/repairs/desktop-capture-renderer-*` 目录。回滚脚本只在配置摘要仍匹配时恢复本轮备份，拒绝覆盖之后的用户修改；恢复后正常重开任务中心即可生效。门户与 MeshAgent 的工件、主 PID、重启计数均保持原状。

## 验证结果与限制

- 默认渲染器重开后，侧栏滚动与图表悬停的 11 次 X11 采样全部检出标题红条；275×44 标题区域最高检出 2,828 个红色像素。
- Cairo 下 60 次被动采样，标题红色像素均为零。首轮 Cairo 自动悬停因检测到外部指针移动而中止，未算作通过；随后独立完成内存页面两处悬停，目视确认提示框文字、背景和边缘完整，标题及图表正常。指针仅在仍停留于本轮测试位置时恢复，未覆盖后续外部移动。
- Windows `jiang-chenx` 的 Edge 155.0.4283.62 经真实门户、代理及中继控制 `lerrem`，首轮 108 次绘制的标题条纹检测为零；2K / Q90 首帧、两次画质切换、一次注入解码失败后的同会话恢复、普通结束均通过。该远端探针不发送目标键鼠，不保存桌面图像；本机悬停检查只操作任务中心的侧栏与图表。
- 第二轮在内存提示框显示期间经同一 Windows 链路验证，53 次绘制未检出标题红条；提示框内部 180×80 区域按行检查，最少一行仍有约 73.3% 的暗色背景像素，没有出现原图中横向断裂的整行缺口。这是特定位置的像素检查，不能外推为任意文字识别或所有提示框的正确性证明。悬停保持器随后检测到外部指针移动并退出，保留外部位置；远端检查此前已经完成。
- 配置已应用到当前正在使用的目标端，原配置及回滚已备份；既有门户和代理健康、运行摘要与重启计数另行核对。仓库本轮仅补充排查文档，不重新发布包含其他未提交工作的门户或原生工件。

这些结果覆盖本次任务中心条纹及提示框场景，不等同所有应用、GPU、低带宽或长期 G0/G3 正式验收。其他应用若出现类似问题，应先区分原始采集异常与传输／绘制异常，再选择对应修复层。
