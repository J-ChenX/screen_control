# Screen Control 长期内存回收调查

调查日期：2026-09-28。用户现场信息：项目启动约 11 天后出现约 11 GB 内存占用。目标是回收不再使用的资源，同时保持正常远控可用。

## 当前事实与边界

- 原浏览器实现将解码异常、128 个未完成图块、16 MiB 压缩积压、64 MiB 已解码位图超限统一处理为结束会话。这不能解决各电脑 MeshAgent 的长期内存增长。
- 本次采样门户服务组约 30 MiB；echova 代理 RSS 约 402 MiB，其中匿名内存约 397 MiB，已运行约 4.8 天；nix 代理 RSS 约 29 MiB。采样时两台均无桌面采集子进程出现在相关进程列表中。不同工作负载不能直接比较为泄漏证据。
- echova 当前门户与代理 cgroup 的 OOM 计数均为 0；历史文档记录过大幅内存增长和 OOM/节流故障。
- 不能凭单次 RSS 或“运行 11 天”推断全部增长来源。需要区分仍被引用对象、原生资源泄漏、发送积压和分配器保留页。

## 长期服务应采用的回收策略

| 资源 | 生命周期与回收点 | 验证方法 |
|---|---|---|
| 桌面采集、编码与解码缓冲 | 复用有限数量缓冲；每块完成后释放；无桌面会话时退出采集并释放资源 | 活跃缓冲数、字节数、停止会话后回落 |
| 增量图块和发送队列 | 消费变慢时反压采集；过时增量不能随意丢弃，须配合完整画面重建 | 慢客户端压力、画面一致性、队列峰值 |
| 会话、连接、子进程对象 | 完成、取消、超时、失败、断线各路径都清理；移除回调、监听器、定时器与全局引用 | 反复连接/断开后存活对象、FD、线程和子进程数不持续增长 |
| 临时缓存 | 按用途设置字节容量与失效时间；过期条目主动驱逐，不只等待下一次访问 | 无访问时过期条目仍能回收、峰值后缓存容量下降 |
| 托管堆 | 先断开无效引用，再由 GC 回收；必要时按堆增长触发受控回收 | 对比回收前后存活堆、暂停耗时和 CPU |
| 原生分配器 | 完成 free 后，按平台尝试归还空闲页；控制过大缓冲池保留 | 存活分配已下降而 RSS 仍高时检查碎片与空闲页 |

GC 无法清除仍被错误引用的对象，malloc_trim 不能释放仍在使用的块。清理操作应针对资源所有权和生命周期，不能按“内存里的内容比较旧”盲目释放。

### MeshAgent #415：短生命周期子进程对象与堆回收

## 隔离 WebSocket 连接反复关闭与取消（2026-09-29）

新增 `tests/native/websocket_connection_churn.py`，在无代理身份的完整 Linux ASan/UBSan 进程中反复建立回环 WebSocket，分别发送关闭帧与取消尚未升级的请求。使用 `--mode close-end --iterations 10`，旧候选再次在 `ILibDuktape_EventEmitter_ForwardEx_target_removeListenerSink` 报告越界读取，而隔离实验候选完成 10 次且无消毒器报告。回调持有从 Duktape 缓冲区取得的裸指针；`Duktape_PushBuffer` 会在缓冲内构造 `ILibMemory` 头，因此问题不是分配器类型不匹配，而是源对象释放后目标钩子仍访问失效指针。这个 C 边界不受现有 Rust 帧解析器保护。

隔离的 `event-emitter-forward-ownership.patch` 以目标事件钩子对源对象的 Duktape 引用替换裸指针；新建候选通过完整构建、原有协议回环、可读流和计时器检查。新增探针的 10 次关闭与 10 次取消均结束，服务端均收到 EOF，未见 ASan/UBSan 报告；100 次关闭的一次运行也完成，但第 10～100 次之间 PSS 从约 42.9 MiB 增至 63.1 MiB。20 次取消的一次运行从第 2～20 次增加约 3.7 MiB，末尾空闲后强制 GC 仍未明显回落。另有连接关闭未及时产生 EOF 的不稳定运行，尚未完成 1,000 次稳定压力检查。

该强引用方案尚不能进入默认构建：`ILibDuktape_EventEmitter_ForwardEventEx` 还把每个连接的 HTTP 流转发到长期存活的 HTTP 服务对象，若目标钩子不解除，源连接会被持续保活。现有 PSS 变化不能单凭页面驻留量区分可达对象、C 分配与分配器留页；须补充存活对象和监听器计数，并在关闭、取消、目标销毁和服务端长驻路径逐一验证引用解除。实验补丁保留供复现与审查，`build.py` 未接入，生产代理和已登记哈希未改变。

进一步的 `event-emitter-forward-weak-cell.patch` 让目标钩子持有可失效状态对象，并在源 `close` 或终结后把移除钩子推迟到事件循环。同步从终结器移除目标监听器曾使第二批转发在 `ILibDuktape_EventEmitter_listeners_tableinit` 的自旋锁中卡住；调试器栈显示它是在 `removeListener` 回调链内重入。改为延后清理后，直接事件转发的 1,000 次隔离测试每 100 次均回到目标钩子基线，新旧批次 PSS 为约 48–49 MiB；不发 `close` 的 100 个源经 150 轮异步 GC 后也全部终结并解除钩子。旧版在相同直接探针中触发原 ASan 错误，强引用实验则保留 100 个源与钩子。这证明了该对象图中的解除引用，不代表完整代理路径安全。

完整进程的 10 次 `close-end` 复现不再触发原事件转发错误，但 100 次正常关闭在第 8 次附近于 `ILibDuktape_net_socket_ResumeHandler` 报告 ASan 读越界。单纯在流关闭时取消 `resumeImmediate` 未消除错误；再在 socket 断开和终结时撤销底层恢复回调后，同一负载在第 8 次附近停滞（客户端看门狗报告 8 次完成，服务端第 9 次未收到完整握手）。这两项恢复回调尝试未保留为默认补丁。取消请求模式的 100 次运行虽能结束，PSS 上升约 25 MiB；旧基线在同模式也明显上升，不能把增量全部归因于新状态对象。独立 HTTP 服务端探针在旧基线与弱引用候选均复现 `ILibDuktape_HttpStream_OnReceive` 于同步回调后读取失效请求头。由于网络关闭和服务端路径仍未通过，弱引用补丁未接入 `build.py`，不进入部署或生产验收。下一步须先解决并对照这两个 C 生命周期问题，再进行长驻服务对象、取消请求及长期内存验证。

追加的隔离诊断显示，完整 WebSocket 重连崩溃与活动客户端 socket 缺少 Duktape 根引用相关：单独保留请求或 socket 至连接 EOF，100 次交叠关闭均通过。`net-socket-active-root.patch` 在客户端连接开始至断开、服务端接受至断开期间保存根引用；`http-callback-lifetime.patch` 在同步 HTTP `end` 回调前保存请求头判断值，并让延迟监听器清理持有消息对象，取代对临时缓冲裸指针的 canary 读取。先只修请求头会暴露后一个 ASan 错误；补齐两处后，HTTP 100 次通过，但约第 379 次请求仍会超时。补齐服务端接受连接的根引用后，HTTP 1,000 次完成，长驻服务对象钩子由 5/6 到 10/11，采样时只有当前请求的一个活动根。客户端 1,000 次快速重连也完成，每 100 次后的根数均为 0，PSS 从 52,938 KiB 到 55,674 KiB，未见 ASan/UBSan 报告。这是完整进程回环的隔离候选结果，未接入默认构建。

取消请求仍有独立增长：同一候选 100 次取消从 41,781 KiB 到 61,017 KiB，所有批次活动 socket 根数为 0。30 次诊断分别观察到请求对象 30 个均进入终结、约 29 个 socket 进入终结，事件链模块维持在 6–7 个，但 PSS 从约 40,082 KiB 到 46,450 KiB；ASan 存活分配字节也由约 2.98 MiB 增至 5.58 MiB。额外 150 轮串行 GC 与超过默认空闲超时的等待未使这一趋势回落；改用共享 Agent 也未改变斜率。相同 20 次负载的 ASan 分配画像中，取消从约 2.91 MiB 增至 5.54 MiB，正常关闭仅从约 2.56 MiB 增至 2.72 MiB；差异主要集中于每次产生的 HTTP 流、socket 属性表和事件监听器对象。隔离尝试在取消时主动解除三条 `pipe` 关系后，链模块数由约 7 降至 4，但 30 次取消的存活分配仍从约 2.94 MiB 增至 6.22 MiB，因此该尝试未保留为补丁。

进一步的事件计数显示，`ILibDuktape_readableStream_Closed` 先发 `end` 再发 `close`，而 `ILibDuktape_Agent_connectionEnded` 在 `end` 内调用 `removeAllListeners()`。20 次取消的普通监听器收到 20 次 socket `end`、0 次 socket `close`，请求 `abort` 也为 0。不过，源码核对表明无参数的 `removeAllListeners()` **只删除非基础设施监听器**；不能由普通监听器的计数推断全部内部 `close` 回调均未运行。只删除该调用的隔离尝试在首轮后触发 `ILibAsyncSocket_PreSelect` 的 `FD_SET(-1)`、UBSan 负移位与缓冲溢出。继续查看发现 `PreSelect` 会在首次检查 fd 后释放锁调用超时回调，回调可能关闭 socket，进入 `FD_SET` 前缺少二次检查；临时加入复查可消除该次崩溃，但移除 `removeAllListeners()` 后 2 次取消仍保留 2 个活动 socket 根，20 次负载的服务端在第二次请求前超时，故两项尝试均未纳入补丁。

另一组隔离实验保留原 `removeAllListeners()`，只把请求 `abort` 的 `close` 回调标为基础设施；20 次取消全部结束且无 ASan/UBSan 报告，但 ASan 存活分配仍从约 2.91 MiB 增至 5.33 MiB，活动 socket 根保持 0，末次采样的计时器根为 37。再把 HTTP 流的 `close` 清理回调也标为基础设施，存活分配约从 2.91 MiB 增至 5.55 MiB，末次计时器根为 35。两组实验都未解决持续增长，也没有证明 `abort` 与 `close` 的完整用户可见语义，均未保留为补丁。重复诊断中，20 次取消的末次计时器根也曾回到 1，但存活分配仍增加约 1.9 MiB；枚举显示额外根为待执行的 `setImmediate`，不能仅用采样时的计时器根数解释增长。

对请求对象加测试专用身份计数后发现，5 个不同请求对象在取消后共进入 22 次 `~` 回调，单个对象最多 8 次。一次性终结补丁的初版在通用事件发射器的终结回调入口清除对象终结器，让该事件只执行一次。叠加活动 socket 根、HTTP 回调和弱状态转发补丁的 Linux ASan/UBSan 候选，20 次取消的请求与 HTTP 流均恰好终结 20 次，存活分配从约 2.91 MiB 回到 2.84 MiB；100 次取消完成，请求恰好终结 100 次，活动根为 0，第 10 至第 100 次的存活分配约从 3.85 MiB 到 4.22 MiB。300 次取消时，采样匿名内存从第 90 次约 37.6 MiB 到第 300 次约 37.4 MiB，未持续上升，但瞬时存活分配在约 6.2–7.5 MiB 间波动。1,000 次正常关闭后活动根仍为 0，请求和 HTTP 流均恰好终结 1,000 次，第 100 至第 1,000 次的存活分配从约 2.84 MiB 到 2.73 MiB；长驻 HTTP 服务的 1,000 次请求也完成，钩子数量保持原有基线，未见 ASan/UBSan 报告。这些数值属于初版隔离候选，不能直接算作后续修订版的通过结果。

去掉所有测试钩子、仅应用三个仓库补丁初版的干净候选，另外完成 300 次取消、100 次正常关闭、1,000 次 HTTP 服务端请求及计时器和流管道回归。300 次取消的匿名内存在第 90 至第 300 次约为 37.6→37.4 MiB，PSS 因其他映射波动；新增的可复现请求终结检查在初版干净候选的 20 次取消后计数为 20，在未修的弱状态候选中为 112。这些是隔离进程证据，不能代替较长时段、独立审查、Windows 与实机会话验证；三个实验补丁均未接入默认构建或部署。

同一回环脚本的 300 次取消对照进一步区分了趋势：未叠加活动根、HTTP 回调和一次性终结三补丁的弱状态候选，匿名内存从第 30 次的 32,500 KiB 增至第 300 次的 83,724 KiB；三补丁初版干净候选从 32,648 KiB 到 37,416 KiB，且第 90 至第 300 次基本持平。两个候选运行于独立进程，负载和采样点相同；这支持初版三补丁组合消除了该短时复现中的持续增长，不能单独归功于 Rust 或宣称覆盖原 11 天故障窗口。

同一初版干净三补丁候选继续完成 1,000 次取消，每 100 次的请求终结计数与连接数一致；第 100 次至第 1,000 次的匿名内存为 46,740→47,576 KiB，各批次在约 46.4–48.2 MiB 间波动，PSS 为 60,745→61,021 KiB。该负载没有重现未修候选在 300 次内的线性增长，但仍远短于原现场故障窗口。

另发现独立的无效 fd 风险：`ILibAsyncSocket_PreSelect` 首次检查 fd 后释放锁执行超时回调，回调可同步关闭 socket；函数重新加锁后未复查，仍把 `-1` 传给 `FD_SET`。无代理身份回环脚本以 `setTimeout(1)` 的回调调用 `socket.end()`，旧 ASan/UBSan 候选在第一次连接稳定报告负移位。`async-socket-preselect-disconnect.patch` 在回调返回并重新加锁后发现 fd 已关闭就解锁退出；隔离候选的 300 次断线均收到 EOF，且 20 次取消、100 次正常关闭和 1,000 次 HTTP 请求通过，未见消毒器报告。该补丁尚未进入默认构建，Windows、实机会话和独立审查仍未完成。

一次性终结初版还有冻结对象缺陷：`Object.freeze()` 后，终结阶段清除 finalizer 的写入失败，10 个冻结事件发射器的 `~` 清理回调有 0 个执行，普通与密封对象各执行 10 次。只把“一次性”标志移入原生事件发射器、但保留 JS 对象 finalizer 的尝试，虽让三类对象都执行一次清理，300 次取消的匿名内存仍从 32,924 KiB 增至 90,420 KiB，因此也已撤销。当前 `event-emitter-finalizer-once.patch` 同时使用原生标志和受保护的清除调用：普通对象能移除终结器，冻结对象即使写入被拒绝也执行一次清理。三类对象各 100 个均恰好终结一次；四补丁隔离候选的 300 次取消中请求计数为 300，匿名内存从第 90 次的 37,304 KiB 到第 300 次的 37,824 KiB。继续至 1,000 次取消，请求计数为 1,000，第 100 至第 1,000 次匿名内存为 44,744→47,048 KiB，未复现单独原生标志版的持续增长。直接事件转发的 1,000 次显式关闭与 100 次仅靠 GC 回收保持钩子基线，100 次超时断线和 1,000 次长驻 HTTP 请求也通过，未见 ASan/UBSan 报告。Windows、实机会话、更长时段稳定性与独立审查尚未完成。

冻结对象的首次压力采样在默认 ASan 配置下每创建 100 个对象并执行 30 轮 `_debugGC()`：100 至 1,000 个对象的匿名内存从 63,312 KiB 增至 180,128 KiB。未修改版与初版补丁呈相近斜率，但这不能证明是对象泄漏，因为零对象、只重复 GC 的对照也在每 30 轮增加约 6.9 MiB。关闭 ASan 隔离区后，零对象对照 5 批匿名内存均为 23,776 KiB；普通和冻结事件发射器各 500 个的后段也稳定在约 24,076 和 24,080 KiB。回归脚本因此增加 1,000 个冻结对象的独立进程检查，关闭隔离区后全部执行一次清理，第 300 至第 1,000 个对象匿名内存只增加 144 KiB，无 ASan/UBSan 报告。这约束了该复现的回收趋势，不能代表所有终结器类型或长时真实代理负载。

审查弱状态转发补丁时又发现 `close` 后的清理时序缺口。源在 `close` 回调中只安排下一轮移除目标钩子，状态里的源裸指针仍有效；目标此时新增 `ping` 监听器会在已关闭源上留下代理。关闭前已存在的目标监听器也会在延迟清理后留下源端代理：两个隔离对照分别得到源端残留 1 个、目标钩子已清空，且源再次发 `ping` 仍会调用目标监听器。修订版在 `close` 时同步失效指针，延迟清理时只移除转发创建的源端代理。关闭前已有和关闭瞬间新增监听器各 100 次均无代理残留，用户监听器仍保留；同一目标由两个源转发时，关闭第一个源后旧候选仍有 1 个代理并误转发一次，修订版为 0 且第二个源正常转发。同一函数重复注册两次、移除一次再关闭时，源端代理从 2→1→0，目标自身仍保留一个监听器。每条转发关系现分别保存原函数与代理函数，避免旧版单个 `proxyFunc` 属性被另一个源覆盖。

这次修改首次运行完整 HTTP 服务回环时，首个请求即在 `ILibDuktape_readableStream_WriteEnd` 触发 ASan 越界读取。根因是 `ILibDuktape_EventEmitter_ForwardEventEx` 被 HTTP 调用时传入相对 Duktape 栈索引；新代理登记在栈上增加对象后继续使用相对索引，取错源或目标。入口固定为绝对索引后，1,000 次长驻 HTTP 请求通过，目标钩子从 5/6 到 10/11，未见 ASan/UBSan 报告。直接转发 1,000 次显式关闭后每批目标钩子回到基线，PSS 后段约 42.9 MiB，100 次 GC 兜底也通过；300 次请求取消、300 次正常关闭、100 次超时断线及普通、密封、冻结对象各 100 次终结检查也通过。该结果仍属隔离候选，不能据此宣称真实代理会话或长期 OOM 已验收。

延迟清理还依赖可由脚本覆盖的全局 `setImmediate`。故障注入在转发建立前或关闭前把它替换为抛错函数，旧候选的每次关闭都吞掉调度错误，源端 `ping` 代理、`close` 钩子和目标钩子在 GC 后仍保留；各 10 次对照共 20 次残留、20 次覆盖函数调用。修订版直接构造固定 `Polyfills.c` 的原生立即计时器入口，继续使用其活动期堆根和触发后清理，不读取全局函数。隔离 ASan/UBSan 回归各 100 次覆盖前后建立转发，共 200 次均未调用覆盖函数，源端和目标钩子回到各自基线；1,000 次长驻 HTTP 请求仍通过。初次测试误以为目标自身的基础设施 `removeListener` 钩子基线为 0，报告 200 次“残留”；记录实际基线后，该钩子未增加。这只验证了被覆盖的全局调度函数场景，原生计时器本身仍需跨平台和取消路径审查。

独立审查又指出关闭钩子本身的注册顺序：原生 `on()` 先通知 `newListener`，再把钩子插入内部表。源对象的用户 `newListener` 回调若在注册 `close` 时同步发出 `close`，旧实验候选会返回转发成功并保留源端代理、关闭钩子及目标钩子。新实验补丁先把基础设施钩子插入内部表，再通知元事件，并在注册期间关闭时返回失败；100 轮同类回归均没有代理残留或误转发。现有关闭回归、1,000 次 HTTP 回环和 22 个 WebSocket 网络用例在 Linux ASan/UBSan 候选中通过。此结论不覆盖脚本对原生元事件的所有重入方式，当前候选未进入默认构建或部署。

同一源反复建立转发并关闭时，另一处长期保留发生在终结器链：旧候选虽把源端监听器清零，却每轮把新包装挂在旧包装前面；测试专用 C 钩子直接计数，200 轮后链深度从 0 增至 200。修订版在源仍存活的延迟清理中摘除本次包装，若它是链头就恢复先前终结器，若在链中就接通相邻包装。同一源同时转发给两个目标并关闭，连续 200 轮的活跃深度为 2、关闭后为 0，源对象释放时原有 `~` 回调恰好执行一次。进一步测试发现，转发建立后冻结源对象会使恢复终结器的写入被拒绝，初版修订打印未捕获异常；现以受保护调用保留这一层失效包装，源端钩子清零、后续终结回调执行一次。冻结对象不能继续新增转发，故该分支不会形成无界链。链深度钩子只存在于隔离测试二进制，仍须独立审查多种重入和平台行为，不能据此宣称生产内存已稳定。

后续独立复查发现，源对象在 `source.on('ping', proxy)` 的 `newListener('ping')` 中同步发出 `close` 时，旧候选仍返回成功；立即再发 `ping` 可误调用目标一次。即使转发已经建好，连续同步发出 `close`、`ping` 也会在延迟清理前误转发。修订候选为代理增加失效状态检查，并在目标监听器查询、代理注册和两个目标钩子注册后复查；注册期间关闭则返回失败，关闭后立即发出的事件不再调用目标。另有显式 emitter 未声明 `close`、脚本元事件抛错、原生调度失败三种边界：候选分别以源终结器兜底、直接移除原生基础设施监听表、受保护的调度失败同步清理处理。调度故障注入初版暴露了钩子和状态对象被 GC 后仍使用的 ASan 越界，以及清理早于 `on()` 完成导致迟到代理残留；修订版保留调用期栈根，并在 `on()` 返回后发现源已关闭时移除该代理。正常调度与故障注入的 Linux ASan/UBSan 候选各通过 100 轮关闭及多阶段重入检查；正常候选的 1,000 次 HTTP 请求、WebSocket 网络回归及原生终结检查也通过，参数身份和目标 `this` 未被代理包装改变。故障注入只验证这条隔离路径，不能替代长期或跨平台验收。

再次独立复查后，原生计数钩子确认上一版直接删表虽令源端 JS `listenerCount('ping')` 与 `listenerCount('close')` 归零，`HasListeners2` 却分别保留 1；目标 `removeListener` 的原生计数也比 JS 多 1。原因是原生缓存只通过元事件更新。修订候选改为调用固定原生 `removeListener` 入口，正常关闭后源端两项原生计数均为 0，目标原生与 JS 计数相同。另一条故障注入使目标 `newListener('removeListener')` 在待安装钩子真正插入前同步关闭源；上一版同步清理后仍迟到插入 1 个目标钩子。新候选在安装期只标记关闭，等 `on()` 返回后由失败路径清理，目标钩子增量降为 0。故障注入下，源的两个既有用户 `close` 回调均依序执行；20 轮完整关闭回归与原生计数、迟到钩子检查无 ASan/UBSan 报告，正常调度候选完成 100 轮及终结器链回归。恢复原生移除入口后，用户自行让 `removeListener` 回调抛错时，上游会记录该元事件异常，但移除及原生计数更新仍完成。此处仅为隔离候选，尚未完成跨平台链接、真实会话和独立复查。

对上述安装期标记继续独立复审，发现脚本属性 getter 可在同步关闭后抛错，直接越过 C 的 `failed` 清理标签。隔离旧候选中，目标 `listeners`、监听函数 `bind`、源 `on` 和目标 `on` 的 getter 四种路径均返回 JS 异常，源端 `close` 钩子和终结器包装各残留 1；返回列表的长度与索引读取也属于相同未保护边界。修订候选将从登记关闭钩子到目标元事件钩子安装的整段操作置于受保护的 C 调用内；外层在异常或普通失败时统一解除安装标记并清理。六种故障注入在正常与原生调度失败候选中均返回建立失败，源端 JS/原生关闭计数和终结器深度均为 0，未见 ASan/UBSan 报告。补丁可无模糊重放到固定源码并与受测 C 文件逐字一致；完整网络和长期会话仍需对最终版本重新验证。
