# Rust 引入评估：按可获得的提升排序

日期：2026-09-28。性质：实施前技术评估与建议；其后的 Rust 原生候选、工具链和验证进度见[原生远控安全核心](../modules/remote-desktop/native-safety.md)，本报告不代表部署或正式验收。

## 结论

建议扩大 Rust 的使用范围，优先覆盖原生远控内核、端点资源管理与文件数据面。排序依据是能消除哪些错误、缩小多少高权限不安全代码面、改善哪些资源生命周期，而非迁移是否复杂。对于已有 Go 控制面，Rust 仍有并发安全和类型约束收益，但对当前原生代理内存问题的直接作用较小。

建议目标是：React/TypeScript 门户，Rust 端点与远控核心，按收益逐步引入 Rust 的会话/传输逻辑，保留经过验证的 Go 身份接入和控制面实现。此处描述职责，不要求把所有 Rust 能力合并到一个进程；桌面系统权限与普通用户文件权限必须继续分离。

现有[技术选型 §2.1](../tasks/private-web-remote/TECHNOLOGY_EVALUATION.md)以适配、构建面为由不选 Rust，并称它不改善远控内核问题。这一判断需要收窄：**只替换 Go 外围服务确实不能修复 C 内核；替换内核中的 C 实现则可以直接减少内存不安全代码。** 旧文档的工程量理由不作为本次技术价值排序的依据。旧 §3.4 的首版范围限制仍是历史决策，本报告提出重新评估方向，不代表已经实施范围变更。

## 评估依据与限制

- 阅读当前工作区的桥接、身份、文件、浏览器内存处理代码及近期调查记录；工作区已有未提交的内存与剪贴板改动，评估包含这些可见实现，没有覆盖它们。
- [README](../../README.md)已有四台被控电脑、手机控制端和可选 HTTPS 网关；早期架构中的三机描述不作为删减这些能力的依据。
- 正式平台代理、生产身份/租约和文件数据面仍有规划部分。现有 G0 Go 文件进程、桥接实现与规划中的生产模块分别评价，不假定规划已实现。
- 11 天约 11 GB 的现场问题及部署状态来自[源码复查记录](MEMORY_SOURCE_REVIEW_20260928.md)和[内存调查](MEMORY_RECLAIM_20260928.md)。本次未连接远端、未重现实机故障，也未进行 Rust/Go 性能对照。
- 上游资料用于确认语言保证与已报告缺陷，不能替代本项目验收。任何降内存比例、帧率或时延增益目前都没有实测依据。

## Rust 能保证什么

| 目标 | Rust 带来的提升 | 仍需单独设计和验证 |
|---|---|---|
| 内存访问安全 | 安全 Rust 的所有权、借用和边界检查阻止悬空引用、重复释放和越界内存访问；越界仍可能导致 panic | `unsafe`、FFI、依赖中的不健全封装、驱动和系统库不因调用方使用 Rust 就自动安全 |
| 并发内存安全 | 安全 Rust 通过所有权及 `Send`/`Sync` 限制未同步共享写入 | 死锁、事件乱序、旧会话回调、授权撤销与操作提交之间的逻辑竞态 |
| 资源回收 | 把缓冲、文件、句柄和配额放入明确所有者，正常销毁时用 `Drop` 统一释放 | 循环引用、无限队列、长期持有的缓存、遗留异步任务、强制退出与崩溃恢复 |
| 内存占用与时延 | 无需追踪式 GC，为大缓冲生命周期与尾延迟提供更多控制 | 分配器保留页、GPU/浏览器内存、FFI 分配、编码器开销；不能推定 RSS 或 CPU 必然更低 |
| 权限和文件安全 | 可用私有构造器、能力类型与状态类型限制错误调用 | 身份真伪、租约过期、路径穿越、TOCTOU、ACL、持久提交与网络重试语义 |

Go 本身已有 GC 与边界检查，迁移 Go 的收益不能按替换 C 来计算；但 Go 的数据竞争不是编译期排除的，竞态检测也只覆盖实际运行路径。Go 内存模型明确指出，切片等多字数据结构的数据竞争可能导致内存破坏。因此并发密集的 Go 模块迁往安全 Rust 仍有实质增益。[Rust 安全边界](https://doc.rust-lang.org/nomicon/what-unsafe-does.html)、[Rust 并发保证](https://doc.rust-lang.org/nomicon/races.html)、[Go 内存模型](https://go.dev/ref/mem)、[Go 竞态检测](https://go.dev/doc/articles/race_detector)。

Rust 不保证没有内存泄漏。尤其是子进程，Tokio 默认丢弃 `Child` 句柄后进程仍会运行，必须明确终止、等待与回收策略；不能将现有 `Close` 简单改写成 `Drop` 就认定生命周期正确。[Rust 泄漏说明](https://doc.rust-lang.org/nomicon/leaking.html)、[Tokio 子进程生命周期](https://docs.rs/tokio/latest/tokio/process/struct.Command.html#method.kill_on_drop)。

## 模块收益排序

这里的“高/中/低”表示相对当前实现的技术增益判断，不是漏洞严重性，也不是实测性能评级。

| 优先级 | 范围与现有依据 | 内存安全增益 | 主要可获得提升 |
|---|---|---|---|
| 1 | MeshAgent 的 C 网络、分片解析、连接取消、Duktape 桥接、采集缓冲与回调 | 高 | 直接减少手工分配/释放、裸指针和跨线程生命周期错误，缩小系统权限进程内的不安全实现 |
| 2 | 正式平台代理、最小权限辅助进程、跨平台句柄封装（多数仍属规划） | 中到高，取决于实际 FFI 边界 | 用所有权管理句柄、连接及配额；固定能力接口；从一开始约束并发共享状态 |
| 3 | G0 文件进程及未来文件数据面 | 中；现有 Go 已有内存保护 | 显式传输状态、临时对象所有权、句柄权限类型、取消与提交边界；更可控的缓冲生命周期 |
| 4 | Go 桌面会话与中继 | 中，主要是并发保证 | 减少共享可变状态，把会话、连接、任务和配额绑定；改善关闭/到期/撤销交错时的可推理性 |
| 5 | 身份、网关、控制面 | 低到中；租约状态逻辑可达中 | 用类型区分已验证主体、租约、能力和未验证输入；减少无效状态；性能收益需测量 |
| 6 | SyncClipboard | 整体重写的增益未证实；局部原生边界可能较高 | 可针对图片处理、原生句柄或大数据处理替换具体组件；历史缓存和通知生命周期仍需独立修复 |
| 7 | React/TypeScript 门户整体、通用运维脚本 | 低 | 保留现有界面；只有独立二进制解析或计算热点适合进一步评估 Rust/Wasm |

### 1. 远控内核：最高收益应落到实际 C 路径

仓库的[候选补丁](../../deploy/g0/meshagent/native-memory/native-memory-backport.patch)涉及 WebSocket 分片释放、请求取消、Duktape 缓冲边界、栈分配对齐、线程回收及子进程对象终结器。[上游 #406](https://github.com/Ylianst/MeshAgent/pull/406)报告了旧分配器的栈缓冲溢出及取消路径泄漏；[#415](https://github.com/Ylianst/MeshAgent/pull/415)针对子进程对象产生速率与 GC 回收的失衡。这些是具体的替换目标，不只是语言偏好。

本地记录说明候选尚未完成真实代理、跨平台与长期验收；本地长期增长根因未完全证明。不能把上游某个场景直接当成本项目全部故障的根因。

建议优先替换完整所有权单元：协议解析与连接生命周期、帧/图块队列、采集会话、子进程与管道管理。仅在 C 代理外增加 Rust 启动器或定时重启器，不能消除内部内存访问缺陷。只替换采集而保留 C 网络/脚本桥接，也要明确剩余风险。

三种路线均应进入比较：

1. **在 MeshAgent 内替换边界清楚的 C 子系统。** 可逐块减少原生风险；C/Rust 交界必须明确长度、所有权、分配释放方、回调存活期及线程限制。安全收益限于实际替换部分，同进程剩余 C 仍可破坏内存。
2. **评估 Rust 为主的现成远控内核。** RustDesk 可以重新进入候选，按当前版本验证网页接入、登录前/安全桌面、Tailscale 路径和仅桌面能力。它的采集与主程序清单仍含平台绑定、`bindgen`、`kcp-sys` 等原生边界，不能视为纯安全 Rust。[采集依赖](https://raw.githubusercontent.com/rustdesk/rustdesk/master/libs/scrap/Cargo.toml)、[主程序依赖](https://raw.githubusercontent.com/rustdesk/rustdesk/master/Cargo.toml)。本次未完成产品适配或依赖安全审计，不能据此选定替代品；旧网页授权判断也需重新核实。
3. **实现限于既有能力的 Rust 桌面代理。** 对协议、队列、权限与资源生命周期的控制最大，应作为技术收益上限方案评估。操作系统采集/输入与编码器仍需不安全边界，须保持最小封装；涉及更大原生库时可评估隔离子进程，隔离收益来自进程与权限设计。

比较三者时记录被移除的 C 路径、残留 FFI、输入可达性、运行权限与故障影响，而不是只比较 Rust 代码占比。不因工作量否决方案，也不因 Rust 占比高就跳过功能与安全验收。

### 2. 平台代理与文件数据面：值得主动采用 Rust

正式平台代理的职责见[模块入口](../modules/platform-agent/README.md)。句柄、任务、租约和连接的所有权适合在实现初期用 Rust 表达；保持系统桌面代理、普通用户文件代理和最小辅助进程的权限边界，不能为了复用合并成系统权限大进程。

当前[文件进程](../../internal/g0files/worker.go)已校验 1 MiB 帧限，[传输窗口](../../internal/g0files/transfer.go)使用 256 KiB 块、最多 8 块窗口；[文件夹处理](../../internal/g0files/folder.go)已经使用 `os.OpenRoot`、隔离目录和延后创建链接。Rust 迁移必须保留这些保护，不能退化为拼接字符串路径后直接打开。[Go 的目录句柄安全说明](https://go.dev/blog/osroot)。

具体增益是将当前分散的 `upload`、`download`、计数器与临时文件状态改为不可随意构造的状态模型：接收中 → 校验通过 → 已提交/已取消。让提交消费临时对象的所有权，减少重复提交、忘记释放和混用对象。持久化一致性、断电、目录替换及跨进程重放依然需要显式处理；类型系统不能替代操作系统句柄语义或磁盘事务。

Rust 文件进程可先兼容既有 SSH 标准流帧协议，在隔离测试目标替换同一职责，避免首步引入新监听或 Go/Rust 内存 FFI。兼容现有 G0 协议不代表生产数据面已通过验收。单纯把相同有界 Go 循环翻译成 Rust，不足以声称显著降低文件传输内存。

### 3. 会话、身份和控制面：有增益，收益机制不同

[桌面会话](../../internal/g0bridge/server.go)已有 `sync.Mutex`、原子领取标志、最多 16 个会话、到期与关闭路径；中继每方向一个 32 KiB 复制缓冲，底层库和套接字还会有额外占用。迁移的主要目标应是共享状态与生命周期，而不是把整个会话内存误算为 64 KiB 或宣称消除无限画面缓存。

建议用每会话单一状态所有者、有界消息通道、任务组显式取消和等待，表达待领取/连接中/活动/关闭状态。Rust 编译期约束可以防止部分错误共享；旧事件、断线输入重放和重复副作用仍必须由代次、协议与测试处理。关闭任务句柄不等于任务已经退出。

[真实对端解析](../../internal/identity/peer/resolver.go)使用 Tailscale Go LocalAPI；保留它可继续复用已有验证。未来若迁移到 Rust，也必须继续绑定真实套接字和目的地址，不能改为信任浏览器或转发头。类型可强制“必须先经验证才能构造授权上下文”，但上下文的过期/撤销必须运行时复核。

`go-sqlite3` 当前在带 `tools` 构建标签的[依赖占位包](../../internal/builddeps/tools.go)中引用，不能仅凭 `go.mod` 认定它已经进入在线业务路径。未来选择 Rust SQLite 封装也不自动移除 SQLite 的 C 实现，应另行核对实际链接树。

### 4. 浏览器与剪贴板：先确定收益归属

[浏览器内存管理](../../web/src/features/desktop/memory.ts)当前已有串行解码、背压、完整画面恢复、代次检查及 `ImageBitmap.close()`。这些是队列和资源策略的收益。Rust/Wasm 可用于纯解析或计算核心，但浏览器图片解码、Canvas/GPU 内存仍由浏览器管理；Wasm 自身线性内存与跨边界复制也需要预算。没有热点证据时，整体迁移门户的内存安全增益较低。

SyncClipboard 的[近期修复](SYNCCLIPBOARD_LATENCY_20260928.md)涉及通知重连、旧连接释放和过期回调；历史窗口、图片缓存与原生资源见[内存记录](MEMORY.md)。这些问题不因 C# 改为 Rust 自动消失。若测量定位到不安全的原生图片组件，可优先替换或隔离；若增长来自仍被引用的历史与缓存，保留策略和生命周期是直接改进点。

## 建议实施顺序与验收基准

1. **先建立风险与资源基线。** 固定当前版本及现有改动，按进程记录原生分配、存活堆、RSS/PSS、句柄、子进程、队列字节和帧延迟。原始基线、C 修复候选、Rust 候选分开比较，避免把已有修复的收益算给语言迁移。
2. **优先验证 Rust 远控内核路线。** 先选一个完整高风险子系统做可对照原型；继续考察现成内核与自研方案，以实际移除风险和满足原有能力决定路线。现有 C 补丁的验证可独立继续，不必等待语言迁移才修缺陷。
3. **正式端点模块优先考虑 Rust，文件进程作为边界清晰的落地点。** 复用现有协议和权限，验证完成后替换唯一实现；迁移期双实现只作为对照与回滚，不形成永久双协议/双权限体系。
4. **按测量与保证需求扩展会话和控制面。** 如果编译期并发约束本身就是目标，可继续迁移，不必等性能瓶颈出现；但性能改善仍独立举证。

| 维度 | 应比较或验证的内容 |
|---|---|
| 安全收益 | 网络可达、高权限 C 路径是否真正移除；列明直接和传递依赖中的 `unsafe`/FFI，纯业务核心建议启用 `forbid(unsafe_code)`；该属性不覆盖依赖 |
| 解析和内存 | 畸形帧、截断、长度/尺寸乘法溢出、超大解码结果、分片及归档模糊测试；安全索引避免 UB 仍须避免 panic/资源耗尽；FFI 边界用可用的 sanitizer，纯 Rust 核心用 Miri 辅助检查 |
| 生命周期 | 建连失败、取消、超时、结束、迟到回调、慢读端、半关闭及服务重启；句柄、任务、子进程和存活分配在每轮后回归稳定区间 |
| 性能 | 同设备、分辨率、画质、显示内容、网络路径和负载，对比首帧、输入响应 p95/p99、有效 FPS、CPU、队列峰值及结束后的内存；不能以降低画质换取语言收益 |
| 长期增长 | 建议至少 24 小时覆盖性压力测试，再做覆盖原 11 天故障窗口的同负载观察；观察回收后基线与增长斜率，不靠定时重启掩盖增长，也不把短测当作根治证明 |
| 产品与权限 | 四台登记电脑的适用平台、手机浏览器、登录前/安全桌面、网络恢复、文件权限与撤销；普通结束不锁屏，不重放键鼠或文件副作用，不新增终端/音频/提权能力 |
| 发布与恢复 | 固定 Rust 工具链和依赖锁、平台构建、SBOM、可回滚工件；沿用既有环境配置和发布边界；既有 G0/G3 等正式门仍独立验收 |

Miri 是辅助验证工具，不是全部平台 FFI 或全程序正确性的证明，适用限制见[官方说明](https://github.com/rust-lang/miri)。背压、图片尺寸上限和故障恢复也需独立于语言存在；高安全收益即使没有速度提升仍有价值。

本报告形成时只完成源码与官方资料评估；此后已实现隔离的 Rust WebSocket 核心候选并完成局部行为回归，具体范围见[候选构建说明](../../deploy/g0/meshagent/rust-native/README.md)。尚无实机性能对照、跨平台发布或覆盖既有故障窗口的长期验收；候选未部署，也未改变正式阶段状态。
