# 桌面自适应画质与整帧显示

## Windows 适配约束

Windows 移植沿用同一 JPEG 元数据、增量、反馈及逐帧输入合同。平台无关的发送历史、双帧信用、差异矩形和共享流回退由公共原生实现负责；Linux 只保留 X11／JPEG／管道适配，Windows 只保留 GDI 位图、GDI+ JPEG 与既有写回调适配。Windows 的底向上 BGR24／BGR32 位图按实际行跨度及填充高度验证后直接缩为连续 RGB24，不先按旧比例拉伸，不改变物理显示模式。

Windows 采集线程是协议状态、选屏及输入映射的唯一写入者。既有输入线程和控制台调用只向有界控制队列写入字节，采集线程先完整消费可用命令，再判断两秒反馈超时；分片残余须压紧，非法长度或队列溢出结束流。暂停及信用耗尽时仍消费控制消息；发送回调背压继续使用既有暂停机制。一次采集最多一张 JPEG，无无限采集或解码队列。

输入继续经过现有服务端权限过滤。鼠标以实际展示帧的有界历史映射到选中屏幕，再加屏幕相对虚拟桌面的有符号原点；输入映射前检查桌面身份、尺寸和布局，切屏／尺寸改变立即作废历史，新点击、移动和滚轮拒绝，释放只作用于最后有效位置。前端在首图确认前抑制组件的旧式启动参数；确认旧代理后释放当前参数，Windows 旧代理继续使用其原有缩放兼容路径。

构建复用固定上游压缩包、现有 Rust C-ABI 和 VS2022 入口；候选、源文件及静态库均绑定摘要。部署沿既有守护，使用实际运行工件作为显式回滚基线，先备份工件、身份及守护，再建立独立 SYSTEM 自动回退；真实多屏、四档、双视口、暂停恢复、普通退出和健康检查通过后保留。Windows 同负载新旧对照单独记录带宽、处理耗时、展示尾延迟与静态画质，Linux 数字不能作为 Windows 证据。以上为移植设计约束，尚不代表实现或部署通过。

## 增量传输优化（2026-10-22）

Linux 沿用既有 JPEG 4:4:4；Windows 隔离候选沿用 GDI+ JPEG 4:2:0，采样及矩形边界限制见上文专项验证。本轮保留 2K 边界、普通用户输入权限和原生双帧信用，不引入视频编码、服务或网络入口。当前基线与合成场景对照必须同时记录流量、处理耗时和画质，真实网络与合成限速分别报告。

能力协商后的版本 2 每帧只发送同次采集的一个矩形 JPEG；比较前次已发送的原始 RGB，差异边界按 16 像素对齐，大面积变化回退整帧。浏览器核对矩形尺寸与基线标识，完整解码后在一次绘制中提交；依赖增量不能按独立整帧方式跳过。尺寸、质量切换或基线丢弃后强制整帧，出错保持旧画面并请求完整恢复。不得通过放宽内存预算或无限增加在途帧取得表面帧率。

旧客户端继续使用版本 1；共享流中收到旧式刷新或反馈超时后，该次 KVM 流固定回退版本 1，避免新旧查看者反复争夺编码模式。新版恢复使用独立的整帧请求，不能冒充旧客户端刷新。原生采集资源只能在尺寸、深度与显示身份一致时复用，切换或退出必须释放。

本轮原生工件已部署到在线的 lerrem、echova、nix，门户同步完成更新；Windows 已完成原生增量移植、真实 JPEG 与输入验证、自动／显式回滚演练和保留，保留后双视口六轮新会话与守护健康通过。当前工件及范围见[运行清单](../../deploy/g0/meshagent/rust-native/adaptive-runtime-manifest.json)。这是既有桥接环境的可回滚运行更新，不表示 G0/G3 或长期正式验收通过。

### 独立画质与采集间隔策略（2026-10-22）

同一策略入口现分别控制分辨率、JPEG 质量和采集周期。分辨率仍采用下文已有的观察窗口、紧急保护及升档退避；固定分辨率不随负载改变。JPEG 质量仅按展示确认压力调整，采集周期同时响应采集／编码、解码和传输压力，因此单纯处理稍慢不会无故降低 JPEG 质量。

展示压力至少 160ms 或平滑处理耗时超过 40ms，持续 600ms 后开始微调；每项调整要求至少三个相应的真实样本，真实本地积压也可直接放慢采集。JPEG 在确认压力至少 160ms 时每次降低 5，最多三个级差，最低 Q60；采集周期在 40／60／80／120ms 间逐级调整，达到处理耗时的 1.1 倍和展示压力的一半后停止继续放慢。每项下调至少间隔两秒；新鲜健康反馈持续四秒后，质量与周期逐级恢复，恢复至少间隔四秒。分辨率严重保护不等待这些微调结束。

已展示基准有效、没有待解码／待绘制图片、也不处于恢复时，静止窗口可以请求一次 Q90 完整基准；窗口为至少 1.5 秒且超过当前反馈观察期的两倍，避免把慢链路在途误判成静止。进入高清补帧时重新累计连续拥塞样本，单个补帧回执不能沿用静止前计数而触发恢复循环。没有新反馈时不逐级恢复采集频率，不因静止反复发配置。大面积运动恢复或连续传输拥塞时退出高清补帧状态。切换普通／流畅及手动分辨率立即重置微调，重新按当前配置观察。配置仍复用既有压缩消息，类型 130 不追加旧刷新；原生收到合法配置后强制完整帧，不改变双帧信用或浏览器内存预算。

## 当前目标与边界

2026-10-20 用户实测指出固定 1080p 明显降低文字清晰度，最高档恢复为 2K；此前 1080p 观察部署已撤回，历史验证仍保留其适用范围。当前方案为优质网络优先 2560×1440，资源不足依次降低到 1080p、720p、540p。真实源不足当前档位时不放大，保持原始比例，不修改物理显示模式。

| 档位 | 16:9 编码边界 | 默认基准 JPEG 质量 | 流畅优先基准质量 |
|---|---:|---:|---:|
| 1440p | 2560×1440 | 90 | 85 |
| 1080p | 1920×1080 | 85 | 80 |
| 720p | 1280×720 | 80 | 75 |
| 540p | 960×540 | 75 | 70 |

16:10 的 2880×1800 源在最高档输出 2304×1440。原生 2K 源使用 RGB24 逐行直接复制，不重复插值；降档使用像素中心对齐的双线性缩小。JPEG 有损压缩仍存在，不能将 Q90 称为无损。更高质量增加带宽，需同时检查编码耗时、发送反馈与解码积压。

## 管线与所有权

目标代理负责 X11 采集、源像素转换、缩放、完整或单矩形 JPEG 编码、尺寸代次、发送历史及逐帧输入映射。门户继续透明转发既有桌面 WebSocket；没有新增服务、监听、源站或身份入口。浏览器负责有界解码、完整画面提交及反馈，只改变所展示画面的缩放，不修改目标显示设置。

一张 JPEG 对应同次采集的一帧，元数据与图片通过同一有序桌面通道发送。v1 使用完整 JPEG，协商 v2 后允许依赖上一已发送基准的单矩形 JPEG；没有变化时跳过重复编码，发送前不积压无限原始帧。局部变化可以减少流量，大面积变化仍发送完整帧。协议字段及输入权限见[桌面扩展](../appendix/protocol-contracts.md)。

尺寸变化时保持旧画面，直到完整新 JPEG 已解码才在同一刷新周期内切换。完整帧原点为零，增量原点及矩形范围必须匹配元数据；JPEG SOF 和实际解码尺寸均须一致。不完整或不匹配帧不确认展示，释放后返回丢弃反馈并恢复画面。代次是不透明标识，原生子进程重新启动后生成新代次；旧解码结果不得覆盖新画面。

输入仍使用既有鼠标命令 2，追加实际展示帧标识，继续经过原只读／控制权限过滤。目标逐包查询有界发送历史进行坐标映射，不能拿另一位查看者最近 ACK 的尺寸来解释本客户端的输入。失效画面不能产生新点击；释放鼠标键仍可在最后有效位置执行，防止卡住拖动。键盘、文件及锁屏边界未扩大。

## 自适应与资源预算

基准采集周期为 40ms，独立策略可逐级调整至 60／80／120ms；采集、转换、缩放和编码耗时计入所选周期，不再处理完后额外固定等待 40ms。实际帧率仍受系统、带宽和反馈影响；540p 仍过载时不通过无限排队冒充流畅或报告稳定 25 FPS。

策略每 200ms 检查一次，队列、解码与展示反馈使用 80% 旧值、20% 新值平滑。静态或尚无可靠活动信号时，清晰优先不再仅因编码超过 60ms 降档：编码稍慢但展示没有积压时保留分辨率，实际帧率仍取决于处理能力。自动分辨率按已展示画面的变化量选择降档条件，始终要求实际延迟超限；动态内容本身不会降低分辨率。

| 普通模式下的画面状态 | 展示压力门槛 | 持续观察 | 两次普通降档的最短间隔 |
|---|---:|---:|---:|
| 静态或小范围变化 | 320ms | 4 秒 | 5 秒 |
| 尚无可靠活动信号 | 240ms | 3 秒 | 5 秒 |
| 连续大面积变化 | 160ms | 1.6 秒 | 3 秒 |

高动态时，平滑后的采集、转换、缩放和编码耗时也参与同一 160ms 门槛，避免链路没有积压但处理本身过慢时继续维持低更新率；高动态恢复升档要求展示压力与处理耗时均低于 80ms。静态及未知状态仍只按展示压力判断，恢复门槛分别为低于 240ms、80ms，让动态结束后的中等延迟画面也能恢复清晰度。流畅优先保留独立门槛。

浏览器最多每 200ms 将已展示画面缩小到 32×18，只在本地比较相邻有效采样的 RGB 差异。平均通道差异至少 16 的采样点计为变化，变化比例不超过 4% 持续一秒后视为低动态，至少 12% 持续 400ms 后视为高动态，中间区间保持已确认状态。首次采样、尺寸变化或采样间隔至少一秒时重新建立比较基线；活动反馈过期一秒或采样不可用时使用普通条件。状态变化重新观察普通拥塞，避免沿用另一门槛的计时。只保留一份 32×18 比较数据，不读取鼠标移动量、不上传像素；采样失败不影响绘制和展示反馈。小窗口视频等小范围动态可能仍归入低动态，这是整屏变化量估计，不是内容识别。

以上普通降档还要求连续至少三个拥塞样本；实际待绘制队列可独立证明积压，无需等待新的完整帧样本。流畅优先仍采用 100ms 展示压力或平滑编码耗时超过 60ms、持续一秒的条件，普通降档至少间隔三秒，不随画面活动改变。

低帧率链路的展示反馈按实际到帧间隔和展示确认耗时保留，观察窗口为一到十五秒；相邻反馈间隔达到十五秒后重新累计。这样每数秒才收到一帧时仍能识别连续拥塞，不会因为固定一秒过期而始终停在 2K。活动量的一秒过期规则继续独立生效，单个迟到反馈仍不足以触发最低档。

单个迟到的 ACK 不再直降最低档；本地待绘制队列达到 500ms，或至少三个连续严重展示反馈使 500ms 压力持续一秒，仍可快速进入 540p，紧急切换至少间隔一秒。达到对应活动状态的恢复门槛（流畅优先为展示压力低于 40ms 且编码低于 32ms）稳定八秒后才逐级恢复；升档后 15 秒内再次降档，下一次恢复观察期加倍至 16／32／60 秒，减少临界带宽下反复试探。没有变化的静止画面仍能通过计时器恢复高清；手动切回自动会重新从最高 2K 起步。

压缩设置由一个策略入口控制。“分辨率”默认自动，手动 1440P／1080P／720P 固定档位后不参与自动切换；“流畅”改变自动策略优先级，固定档位时仍可独立调整 JPEG 质量及采集周期。共享 KVM 流的查看者会跟随实际生效的源档位，不宣称每位查看者拥有独立编码流。

浏览器保留 8 Mi 像素、最多四个解码／待绘制名额；2560×1440 实际最多两张，释放前继续占预算。保留既有压缩字节／图块数量保护及完整刷新恢复。原生最多允许两帧尚未取得展示／丢弃反馈；刷新不能凭空释放信用。共享流中最后一个新版客户端离开后，窗口满且两秒没有反馈时退回旧客户端兼容发送，避免旧查看者永久卡死；此期间不承诺两帧上限，浏览器预算仍生效。
