# 原生远控安全核心

## 职责与边界

在固定 MeshAgent 源码中替换网络帧处理的 C 算术、未对齐读写与缓冲管理。Rust 负责安全解析和字节变换；C 适配层只传递明确大小的数据并继续使用既有连接、身份和桌面权限。此组件是替换现有实现的构建组成，不是新增服务或第二套协议。

WebSocket 帧头解析与掩码覆盖非零接收偏移、部分帧头、扩展长度、整数边界、控制帧约束与任意字节对齐。分片核心拥有重组缓冲和消息序列状态；C 连接、传输队列与平台资源仍由既有实现管理，不能称为完整内存安全代理。

Linux 屏幕帧的 RGB24 tile 复制、变化校验与 XImage 格式转换已纳入候选 Rust 核心：FFI 检查有符号尺寸、填充步长、全部源行、目标容量和区域重叠，再调用不含 `unsafe` 的纯函数。校验只读取 tile 内字节，不再把 RGB24 转为 `int*` 或跨越最后一行；失败时 C 采集循环停止，不能把异常结果当成未变化帧。转换支持 16/24/32 位与两种字节序，并按每行的实际跨度读取；常见 BGRA/BGR/RGB565 使用专门快速路径。XFixes 光标在已转换的 RGB24 帧上由 Rust 有界叠加，超出屏幕的部分裁剪；无法叠加时恢复客户端光标显示。C 侧在分配前检查 tile、共享内存和桌面缓冲的尺寸乘法、空指针及失败结果，共享内存权限限制为当前用户；单帧原始图像和转换后缓冲分别限制为 1 GiB，光标叠加最多接受 1024×1024。X11 资源获取、JPEG 编码与网络发送仍在 C 中；Rust 无法证明 C 传入指针的实际分配范围。

候选主循环已把远端输入记录坐标与当前 X11 指针坐标的比较改为任一轴不同即进入光标叠加分支，避免只沿水平或垂直方向移动时沿用旧代理的双轴条件而跳过光标；X11 指针查询失败或光标显示连接不可用时会恢复客户端光标，不会保持隐藏状态。光标类型识别改用 `XFixesCursorImage` 字段及有界像素数，空图像、缺失像素和过大尺寸均返回默认光标；必要的 XFixes 函数缺失时初始化直接失败，不再调用空函数指针。隔离候选的实际 C 识别函数与主循环光标分支已在 ASan/UBSan 下验证单轴移动、查询失败、空图像、叠加失败及有效图像的 alpha 提取。这些提取式测试未运行完整代理会话；真实远端鼠标移动和客户端光标状态切换仍需验收，不据此宣称完整光标行为正确。

Linux JPEG 编码仍调用固定源码附带的 C 静态库。构建候选优先使用与该库一致的 JPEG 头文件，避免系统头文件版本不同导致实际编码时退出；真实编码和解码已成为构建检查。C 适配层对输入尺寸、输出增长、整数长度及分配失败加界，重复 tile 编码复用输出容量，超过 1 MiB 的暂存容量在发送后释放，主循环结束时清空剩余容量。JPEG 库及采集和封包控制流仍在 C 中，此修复不等于整个采集链内存安全。

## 接口约束

- 输入只读取 C 已确认可访问的接收区间。帧头最多 14 字节，使用定长值传递，Rust 解析核心不借用 C 指针、不分配内存。
- 返回未完整、有效或无效状态；仅在完整有效帧时交给既有消息分发。长度使用受检查的无符号算术，转换为 C `int` 前验证总长度。
- 每帧正文上限与当前桌面中继的 64 MiB 上限对齐；超大帧在帧头可读时拒绝，不等待分配整个正文。文件工作进程的 1 MiB 限额不改变。
- 掩码变换按字节实现并支持任意对齐，不保留 C 指针。FFI 调用方保证输入/输出区域真实可访问，别名规则在适配函数内明确；该契约不能由 Rust 验证。
- 分片按既有重组预算累计，预算超过 64 MiB 或为负时拒绝初始化；超出有效重组预算后以中间/最后分片流式交付，不丢字节。完整单帧直接交付，不额外复制。消息结束后不保留重组峰值容量。
- 输出缓冲从连接状态中移交，独立释放；C 回调期间没有 Rust 借用。独立存活租约允许同步取消释放请求后安全停止后续交付，不能用已释放请求上的字段或 canary 代替租约。
- 请求析构统一释放解码器，原 C 分片缓冲路径已删除；拒绝孤立 continuation、未结束消息中的新起始帧。此检查不代表完整 WebSocket UTF-8、关闭握手和传输层生命周期已验收。
- 不修改登录、会话归属、网络选路、普通结束和锁屏语义。非法帧导致连接失败，恢复不重放输入和文件副作用。

## 验证与发布条件

固定 Rust 候选还叠加了可读流 C 适配层补丁：按目标 `unpipe` 时，前驱或链表头已指向后继，却遗漏 `后继.previous = 前驱`，会留下失效反向链接。隔离的完整代理进程回环检查对 A、B、C 三个 Writable 连续移除 B、C，旧候选虽各发出 `unpipe` 事件，仍把 5 字节送给 C；连续移除 A、B 时，仍送给 B。修复补齐后继反向链接，构建检查要求两个顺序中仅剩余目标收到数据。该问题位于 Rust 核心外的 C 生命周期边界；回环验证不能证明当前生产崩溃由它触发，也不覆盖真实会话。

同一适配层的节点缓冲还被目标 Writable 的隐藏对象缓存强引用。旧实现把每次 `pipe()` 的缓冲对象放入缓存，却在指定 `unpipe`、全部 `unpipe` 和可读流终结器中没有删除；目标长期存活时，节点因仍可达而无法由 GC 回收。候选现保存原 Duktape 缓冲对象指针，按原键在三处解除引用。只注入临时源码副本的 ASan/UBSan 计数测试证明：同一目标重复十次后，旧候选隐藏缓存项为 1–10，新候选每轮为 0；三个目标的指定移除、全部移除及终结器路径分别从旧候选的 `(1,1,1)`、`(1,1,1)`、`(1)` 变为 `(1,0,1)`、`(0,0,0)`、`(0)`。这证明强引用清理，不等同于完整堆回落或长期 RSS 稳定，也不能证明生产 OOM 只由此造成。

隔离脚本还复现了另一处 C 生命周期错误：旧版只为 `setImmediate` 保留 Duktape 根引用，未保存句柄的嵌套 `setTimeout` 只执行第一层；保存两个句柄的对照则两层均执行。候选在参数校验和注册成功后，将 timeout、interval 和 immediate 的活动对象统一保留至触发或明确取消，再解除根引用。完整进程测试核对了未保存句柄的两层触发、`clearTimeout` 后根项为 0、无效延时和回调抛错后根项仍为 0、interval 三次后取消且不再触发，以及五次 immediate 不累积根项。测试钩子只存在于临时复制的源码中；旧版行为的复现不能直接推定生产环境的具体计时器曾被取消，也不能证明整个事件循环无其他生命周期问题。

弱状态事件转发还有注册时序边界：原生 `on('close')` 在把钩子加入内部表之前先发 `newListener`，用户回调可同步发出 `close`。旧候选此时仍返回建立成功，并留下代理和目标钩子。实验补丁先登记基础设施关闭钩子，再发元事件；若注册期间已关闭，建立失败并延后清理。这个顺序有可观察的兼容差异：隔离对照中，普通 `on('close')` 的 `newListener('close')` 回调看到 `listenerCount('close')=0`，转发安装内部关闭钩子时看到 `1`；依赖注册前计数的脚本需在真实会话中核对。无代理身份的 Linux ASan/UBSan 完整进程中，100 轮同步关闭均返回失败且源端代理、关闭钩子和目标钩子回到基线；现有关闭回归、1,000 次 HTTP 回环及 WebSocket 网络回归通过。

同一源重复建立转发并关闭时，旧候选虽然移除了事件代理，却让每次安装的终结器包装继续引用前一个包装：隔离测试钩子测得 200 轮后链深度为 200。修订候选在源仍存活且本次转发清理时，把对应包装从链中摘除并恢复前一个终结器；同源双目标重复 200 轮，每轮同时活跃时深度为 2，关闭清理后为 0，原有 `~` 终结回调最终恰好执行一次。若转发建立后源对象被 `Object.freeze()`，恢复终结器的写入会被拒绝；候选以受保护调用保留这一层已失效包装，关闭钩子仍清零，原有终结回调执行一次且不产生未捕获异常。冻结对象不能再成功建立新的转发，因此该分支不形成持续增长链。测试钩子仅注入隔离候选，不能作为生产指标；补丁仍需独立复查、跨平台构建和真实会话验收。

独立复查还发现 `close` 钩子安装之后仍有同步关闭窗口：预存目标监听器的代理注册、目标 `listeners()` 和目标元事件钩子注册都可能运行用户回调。候选现在于每个阶段复查状态；代理自身先检查源是否仍有效，因此 `close` 后到下一轮移除钩子的间隙也不会再转发。原先直接从内部监听表移除基础设施钩子会使 JS 监听数归零而原生计数缓存仍为 1；修订候选调用固定原生移除入口，由其发送 `removeListener` 并更新缓存，避免脚本替换方法影响清理。隔离原生计数钩子确认源端 `ping` 和 `close` 均回到 0。安装目标钩子期间若同步关闭，即使原生调度失败也先让 `on()` 完成，再由安装失败路径清理，避免迟到插入；故障注入对照从目标残留 1 个钩子变为 0。原生事件发射先克隆回调列表，故障注入下关闭清理未跳过已有的前后两个用户 `close` 回调。显式 emitter 没有 `close` 事件时保留转发，由源终结器清理。正常调度候选通过 100 轮关闭、重入与终结器链测试，调度失败候选也通过 100 轮及新增边界检查，均未见 ASan/UBSan 报告；这仍需独立复查、跨平台和真实会话验证。

安装期关闭还需要覆盖脚本 getter 抛错：目标 `listeners`、监听函数 `bind`、源或目标 `on` 的属性读取，以及 `listeners()` 返回列表的长度和元素读取，都能先同步关闭源再抛错。旧候选四种方法 getter 均绕过安装失败路径，留下一个源端 `close` 钩子和一层终结器包装。修订候选让完整安装阶段在受保护的 C 调用中执行，外层保留源、目标和状态对象的栈根；异常统一转为建立失败并清理。隔离 ASan/UBSan 测试覆盖六种读取边界，均确认 JS 和原生关闭钩子计数归零、终结器包装深度归零。此处仍是候选验证，异常恢复不代表整个 MeshAgent 的 C 生命周期已无其他缺口。

纯 Rust 核心禁止不安全代码。单元与性质测试覆盖所有帧头截断、边界长度、非零偏移及掩码往返；C ABI 在 ASan/UBSan 下验证缓冲边界和未对齐输入。C ABI 测试使用始终执行的 `CHECK`，普通与 `-DNDEBUG` 优化构建均核对非法分片后的状态恢复、超预算时前缀与调用方输入的所有权、输出在状态销毁后的有效性，以及同一状态的多个租约。固定源码补丁必须可重现应用并完成真实 MeshAgent 构建，不能只测独立 Rust 函数。

分片测试覆盖首帧大于旧初始容量、预算边界、流式字节完整性、输出在状态销毁后仍有效、峰值容量回收和重复取消。集成检查逐字提取补丁中的接收与请求析构函数，模拟回调同步释放连接与接收区间；这不代替完整事件循环、真实网络断连和平台退出的验证。

MeshAgent 内另有 Duktape 脚本 WebSocket 接收路径，旧实现对首个 10,000 字节分片只从 4 KiB 扩到 8 KiB，随后安全拷贝检查直接终止进程。该路径现复用 Rust 帧头与有界分片核心，消除未对齐的 C 掩码读取和单次扩容缺陷。脚本流需要完整消息，超过 64 MiB 消息预算时结束连接并记录失败；已协商的 permessage-deflate 保留解压窗口以兼容连续消息，逐块计数并在解压输出超过 64 MiB 时停止解压，不向脚本交付截断前缀。解压器仍来自 MeshAgent 的 C/zlib 模块，Rust 并未覆盖这一边界。构建候选须通过不加载真实代理身份的完整进程回环 WebSocket 检查，覆盖未掩码/掩码分片、穿插控制帧、连续压缩消息、大单帧、非法帧后的对端 EOF 与解压超预算。

同一隔离候选可对 Linux 代理的 C 代码启用 ASan/UBSan 运行回环检查。该检查已揭示并修正链元数据释放、`setImmediate` 越界、Base64 尾块读取、Duktape 缓冲区内存头未对齐读取及脚本堆销毁时的事件转发问题。当前消毒器不插桩 Rust 静态库，也不覆盖其他脚本、平台采集和长期运行；不能据此宣称整个代理内存安全。

连续 WebSocket 关闭在事件转发回调中另复现了 ASan 越界读取：目标钩子访问源对象释放后留下的 Duktape 缓冲裸指针。`Duktape_PushBuffer` 实际含有 `ILibMemory` 头，不能据此归因为头格式不匹配。强引用实验消除原复现却保留旧连接；弱状态对象实验在 1,000 次直接转发中能解除钩子，但完整 WebSocket 关闭又暴露 socket 恢复回调的悬空读取。后续隔离补丁为活动客户端和服务端 socket 保留可解除的根引用，并修复 HTTP 同步及延迟回调的两处裸指针边界。取消路径还发现同一请求对象多次进入事件终结回调；一次性终结初版将 20 次取消的终结计数从未修候选的 112 降为 20，却使 10 个冻结对象的清理回调全部失效。先前版本在原生发射器标记首次终结，并对可修改对象受保护地清除终结器；普通、密封与冻结对象各 100 个均终结一次，另有 1,000 个冻结对象的清理和后段内存回落检查通过。该先前版本的四补丁隔离候选完成 1,000 次取消和 1,000 次 HTTP 请求，取消负载后段匿名内存未持续上升。Windows 对照随后发现，终结回调开始前清除 finalizer 会阻断桌面中继；只保留原生一次性标记虽使短会话重新连接，却在 Linux 300 次取消中产生约 50 MiB 的持续匿名内存增长。当前补丁先执行终结清理，再受保护地清除未被回调替换的 finalizer；隔离候选的 300 次取消后段趋稳，加入身份复查后的 100 次取消也趋稳。Windows 真实连接与较长时段稳定性仍需验证。以上补丁均未接入默认构建，不能计入已修复候选或部署验收。[内存回收记录](../../performance/MEMORY_RECLAIM_20260928.md)保存了隔离探针结果。

原生事件循环还在无代理身份的 socket 超时断线回环中复现无效 fd：超时回调关闭连接后，`ILibAsyncSocket_PreSelect` 继续执行 `FD_SET(-1)`。隔离补丁在回调返回后重新确认 fd 有效；旧候选单次触发 UBSan，修补候选连续 300 次断线收到 EOF，未见 ASan/UBSan 报告。一次性终结初版的三补丁干净候选与当前四补丁修订版都在 1,000 次取消的后段维持相对稳定的匿名内存；当前修订版仍需更长负载、跨平台、实机会话与独立审查。新补丁同样未接入默认构建。

事件转发的 `close` 清理原先只推迟移除目标钩子，既有源端代理未移除，且回调内新增的目标监听器仍会被转发到已关闭源。隔离回归确认目标钩子清零后源端仍保留代理并可继续误发事件。修订版在 `close` 时先失效源指针，再于下一轮按转发关系移除源端代理及关闭钩子；关闭前已有和关闭瞬间新增监听器各 100 次、多源转发及同一监听函数重复注册的回归通过，用户监听器保持不变。初版修订还因相对 Duktape 栈索引在 HTTP 首个请求触发 ASan 越界；固定绝对索引后，1,000 次长驻 HTTP 请求、300 次取消和 300 次正常关闭通过。该结果还需跨平台、实机会话、长稳负载和独立审查，未改变默认构建或部署。

关闭清理原先通过全局 `setImmediate` 调度，脚本可覆盖该函数使其抛错；旧候选虽吞掉错误，却把源对象与转发钩子继续保留。隔离修订直接调用固定源码的原生立即计时器入口。故障注入在覆盖函数发生于转发建立前或关闭前时，旧候选各 10 次均残留钩子，修订候选各 100 次均回到监听器基线，且未见 ASan/UBSan 报告；完整 HTTP 1,000 次回环仍通过。原生计时器的取消与脚本堆销毁边界、Windows 构建及真实远控会话仍须验证，该实验补丁没有进入默认构建或部署。

当前开发机已用 MIT-SHM 对实时 X11 帧作内存内对照：候选真实 C 调用点与直接 Rust 调用输出完全一致，1,024 个像素位置的 RGB 通道与 `XGetPixel` 对照无不一致；测试不保存或展示画面，并在 ASan/UBSan 下通过。此证据只覆盖该开发机的当前像素格式和一帧，不覆盖光标实机交互、异常共享内存路径或长期稳定性。未经这些验证及独立审查不得将候选部署到控屏设备。

`tests/native/run_x11_cursor_live.py` 已在重新构建的固定源码、固定补丁 Linux ASan/UBSan 候选上核对 Rust 静态库及 C 头文件摘要，再读取当前 X11 会话的真实 XFixes 光标像素。16 轮中每轮对未裁剪位置、左上裁剪和右下裁剪作独立 C 逐像素对照，并验证短光标输入及短目标缓冲拒绝且不修改目标；合计覆盖 2,016 个可见光标像素，C 测试进程无消毒器报告。测试只在内存中比较，不移动鼠标、不保存光标或屏幕图像。这证明真实 XFixes 输入可通过当前 Rust C ABI 的边界检查，不覆盖代理主循环的光标状态切换、远端浏览器显示或实际鼠标移动；Rust 静态库本身未插入消毒器。

隔离 JPEG 编解码检查已覆盖 32×32、512×512、2048×2048 图像，较大图像的编码字节摘要与修复前基线一致，2048×2048 图像结束后回收了超过 1 MiB 的输出暂存容量；完整 Linux 候选在 ASan/UBSan 下通过该检查。它尚未覆盖从真实 X11 帧到远端浏览器的完整画面传输、长时间压测或多设备使用，因此不改变部署门槛。

tile 变化校验的真实 C 调用点已验证首帧发送、未变化帧跳过、末像素变化后重新发送和短帧拒绝；有界 Rust 核心覆盖小尺寸、行填充、无效区域和相邻 tile 隔离。旧版校验曾额外读取每行 tile 尾部后一字节，末行可越过帧末；新算法每四字节执行同一乘法，但只处理 tile 内数据，校验值会变化。该值仅用于运行时比较，不持久化或跨网络传递。32×32 内部 tile 的八次交替微基准中，Rust FFI 中位数 0.543 微秒、旧运算的安全 C 对照 0.564 微秒；实际画面变化率和完整帧率尚未测量。

本机探索性热路径测量：1920×1080 BGRA 转 RGB24 的 40 轮 `-O3` 微基准，Rust FFI 为每帧 0.87–0.91 毫秒，安全 C 对照为 0.92–0.96 毫秒；隔离 ASan/UBSan 候选对同一 32×32 内容连续编码 10,000 次为每 tile 13.6 微秒。Linux 管道上的 `fsync` 全部返回 `EINVAL`，未插桩的一百万次调用平均约 61 纳秒；同机 XFixes 获取并释放当前光标的 2,000 次调用平均约 9.1 微秒。仅创建与销毁 JPEG 压缩器在 ASan/UBSan 下为约 219 纳秒。由这些局部结果看，去掉管道同步调用或缓存压缩器对象所能减少的工作量有限，尚无足够收益依据去改变发送和对象生命周期；光标缓存也需先证明实际帧延迟收益并处理失效。不同基准的插桩与负载不同，不能相加推算实际 FPS，仍须在完整远端会话测量。

RGB24 转换曾先清空整块输出缓冲，再覆盖全部有效像素；现在只清空行尾和底部填充，保留无效输入不写入目标的约定。旧、新静态库对 16/24/32 位及两种字节序、不同源/目标步长的 264 组输入产生相同完整输出摘要，C ABI 在 ASan/UBSan 下通过。相同硬件交替运行并预热的 40 轮 `-O3` 微基准中，1920×1080 转换中位数从 0.9465 降至 0.8195 毫秒/帧，3840×2160 从 4.5505 降至 3.5860 毫秒/帧。重新构建的隔离候选完成 4K 动态全帧 600 次采集，转换计时从旧候选单次运行的 6.188 降至 4.590 毫秒/采集帧，后段 PSS 在约 68.6–69.2 MiB 波动、结束后回落；这两次整链运行不是严格配对基准，JPEG 编码仍占主要耗时。4K 合成高细节画面 60 帧生成约 424 MB JPEG，首包在浏览器解码通过，进程结束后 PSS 回落；该负载的编码平均约 117 毫秒/采集帧，不能推算真实桌面 FPS。

开发机当前 X11 显示的左上、中心与右下三处实际画面 tile，已通过固定候选的 XShm 采集、Rust RGB24 转换与校验、C JPEG 编码和协议封包，再以内存管道送入 Chromium。浏览器运行门户实际的 `manageDesktopMemory`，每处连续解码绘制 32 次，与同一 JPEG 的 C 解码逐通道差异为 0；每个 `ImageBitmap` 已关闭，画布结束时缩至 1×1。测试启用 ASan/UBSan 与泄漏检测，重复三轮后未新增 SysV 共享内存段。画面和像素值没有落盘或写入日志。该隔离测试未经过真实登录、远端网络、控制输入或暂停恢复，不能证明完整远程会话与多设备验收。

`tests/native/run_dynamic_tile_live.py` 在自动创建并关闭的 Xephyr 显示中生成 640×480 交替色画面，隐藏其外层窗口，不触碰已登记设备。固定 Linux ASan/UBSan 候选连续采集 60 帧，逐帧执行 XShm、Rust RGB24 转换、32×32 tile 变化校验与 C JPEG 封包；测试要求采集像素持续变化，且每次变化恰好输出一个包、首帧另有一个包。重复运行观察到 32–33 次像素变化与 33–34 个输出包，编码字节总计约 21–23 KiB；采集均值约 0.15–0.29 毫秒、转换约 0.16–0.22 毫秒、tile 校验和编码约 0.02–0.04 毫秒。这是单 tile 的隔离候选调用点测量，没有网络、浏览器绘制或输入响应；计时受 ASan/UBSan 与本机调度影响，不能据此推算完整远控 FPS。

同一测试现逐次运行单 tile 与完整 20×15 网格。全帧交替色的 60 次采集在重复运行中有 33–34 次像素变化，各自产生一个合并的 640×480 JPEG 包，静止采样帧不产生包；JPEG 头部尺寸也在测试中核对。全帧输出约 300–310 KiB，tile 校验与编码调用总计平均约 0.7–0.9 毫秒/采集帧；采集和 RGB24 转换各约 0.17–0.21 毫秒/帧。隔离显示使用临时 Xauthority、禁用 TCP 监听，测试结束关闭动画与显示。这仍是固定颜色、大面积高压缩画面的本地候选测试，未代表复杂桌面内容或网络端到端吞吐。

为覆盖大包边界，测试还在同一隔离显示中交替显示两张确定性生成的 640×480 高细节 PPM 图像。固定候选的 60 次采集中，约 35 次变化产生约 36 个合并的 `MNG_JUMBO` JPEG 包，总编码量约 9.4 MB，tile 校验与编码调用平均约 2.6–2.8 毫秒/采集帧。测试核对 jumbo 长度、画面坐标和 JPEG 尺寸，并把首个合成包经内存管道交给 Chromium 解码绘制；`ImageBitmap` 使用后关闭，画布缩至 1×1。两张合成图像与 jumbo 包均不留存。此证据覆盖候选的本地封包和浏览器 JPEG 解码，不覆盖门户实际的远端协议处理、网络拥塞、复杂桌面交互或长期运行。

性能对照使用同一数据量、掩码、编译优化和硬件，分别记录吞吐、分配和内存。功能对照须覆盖真实连接、桌面画面、输入、暂停/恢复及结束；Linux/Windows 分开验证。当前源码基线及原生回收补丁见[构建候选说明](../../../deploy/g0/meshagent/native-memory/README.md)，已有候选未经长期验收。

部署仅替换已登记服务的工件并保留旧版、配置和哈希回滚；若固定哈希守护需要配套更新，必须保持校验且原子切换。不修改网络规则、信任库或设备角色。长稳验证跟踪同负载回收后基线，覆盖既有约 11 天故障窗口；短测不证明根治。

## 构建一致性

Rust 版本由 `.mise.toml` 与 `rust-toolchain.toml` 同步固定，当前工具链清单绑定 Cargo 清单及锁文件的哈希；`make verify` 会拒绝版本或哈希漂移。CI 的 Linux/Windows 作业编译同一 Rust 核心并运行测试与 Clippy，Linux 另运行 C ABI 消毒器测试；CI 配置不等于 Windows MeshAgent 完整候选已验收。2026-09-29，本机用锁定工具链为 `x86_64-pc-windows-gnu` 完成 Rust 工作区所有目标的 `cargo check`、Clippy 警告即错误检查和 C ABI 发布静态库构建；没有链接 Windows MeshAgent、运行 Windows 测试或验证 Windows C 调用点。现有 SBOM 保留原验收范围，包含 Rust 的完整发布须重新生成工件清单与来源证明。

Windows 图块候选还把底向上位图的图块复制和变化校验移入安全 Rust，实际捕获缓冲长度沿 `get_tile_at` 传递；Rust 在写入前检查像素宽度、坐标、尺寸乘法与两侧容量。固定源码中原有的逐行指针运算与 `util_crc` 读取被替换，GDI 采集、JPEG 和发送仍为原生代码。24/32 位底向上行序、旧校验算法、短缓冲不修改目标的 Rust 测试及 C ABI 检查通过；Windows 原生构建与真实会话尚待核对。

同日为锁定的 Rust 工具链安装 `x86_64-pc-windows-msvc` 标准库目标后，本机另通过该目标的全工作区 `cargo check --all-targets`、Clippy 警告即错误检查，以及 `screen-control-protocol-ffi` 发布静态库构建。生成的 `.lib` SHA-256 为 `00d2da401dc43ce9993229b94f35da0b4c0fca5c004432cc98303d7ba5e9b3d0`；其 15 个 `sc_*` 导出符号与公开 C 头文件声明逐一相符。在线 Windows 主机以 Visual Studio 2022 对固定源码完成 `Release|x64` 全量重建，MSVC 编译的 `tests/native/websocket_abi.c` 链接同一 Rust 静态库并运行返回零。受守护短时切换显示：默认 Rust 核心与前三个原生生命周期补丁均可进入真实桌面“已连接”；加入旧的一次性终结补丁会停在中继连接。只保留原生一次性标记的中间组合再次连接成功，却在 Linux 300 次取消中出现持续内存增长，因此当前补丁改为在清理回调后受保护地移除仍未被替换的 finalizer。修订组合的 Linux ASan/UBSan 隔离测试中，三类对象各 100 个仅终结一次，100 次取消的后段匿名内存趋稳；Windows 原生工程零错误重建；同逻辑的前一构建候选服务短时启动，最终摘要尚未运行。此次控制门户返回 503/502，未取得当前组合的真实桌面连接结果，随后已恢复原工件与守护。画面质量、输入、取消路径长期回收和稳定性仍待验证。可复现准备步骤、二进制摘要和回滚过程见[Windows 候选构建](../../../deploy/g0/meshagent/rust-native/README.md)。
